Partie 02  ·  Deep-dive
Le cluster comme identité unique : extraire les secrets CNO/VCO de WSFC
Windows Server Failover Cluster réplique le mot de passe du Cluster Name Object sur chaque nœud. C’est fonctionnellement nécessaire, et c’est ce qui fait du cluster une cible unique.
Plan de la partie
1
 Ce qu’est un CNO, et pourquoi il est Tier Zero de fait.
2
 Où vit le secret : CLUSDB, checkpoints registre, structure _NNPWD_STRUCTURE.
3
 Le déchiffrement : NetNameLib::CryptoAccessV2::Decrypt dans clusres.dll.
4
 Le pivot RBCD : de Domain Computers à un ticket de service forgé.
5
 Pourquoi Impacket casse : il n’y a pas d’ADMIN$ sur un CNO.
6
 Limites, prérequis, et ce que la rotation horaire ne protège pas.
Garrett Foster a publié le 29 juillet une étude sur Windows Server Failover Cluster qui n’a pas de CVE et n’en aura pas. Ce n’est pas un bug : c’est une propriété de conception dont la conséquence offensive est rarement énoncée. Un cluster de basculement existe pour qu’un service survive à la perte d’un nœud. Pour cela, l’identité du service doit pouvoir être portée par n’importe quel nœud, à tout moment, sans intervention. Donc chaque nœud détient le secret de cette identité. La redondance qui protège de la panne matérielle supprime, par construction, l’isolation entre nœuds.
L’objet central est le Cluster Name Object (CNO), un compte machine Active Directory qui porte l’identité du cluster. À côté, un Virtual Computer Object (VCO) par point d’accès applicatif : une instance SQL en cluster, un rôle de partage de fichiers, un point d’accès ADFS. La base du cluster vit dans C:\Windows\Cluster\CLUSDB et est montée sous HKLM\Cluster. Le processus RHS.exe — Resource Host Subsystem — charge les DLL de ressources et porte les sessions de logon des identités de cluster. Les volumes partagés sont montés sous C:\ClusterStorage.
Foster résume la conséquence sans détour : compromettre un seul nœud vaut compromission complète du cluster. Ce qui compte pour un opérateur, c’est qu’un CNO ne ressemble pas à un compte à privilèges. C’est un compte machine ordinaire dans l’annuaire, sans marqueur particulier. Sa criticité vient de ce qu’il porte, pas de ce qu’il est — et c’est exactement pourquoi il échappe aux inventaires de comptes sensibles.
Où vit le secret. Le mot de passe du CNO n’est pas stocké là où l’on chercherait un secret de service. Il vit dans des checkpoints du registre, chiffré, avec les éléments de déchiffrement à côté. Trois emplacements comptent.
Emplacements registre — base de cluster
HKLM\CLUSTER\[GUID]\CryptoContainerGuid -> identifiant du conteneur cryptographique associe a la ressource HKLM\Cluster\Checkpoints\[GUID]\Crypto\Checkpoints -> materiel de cle, replique sur chaque noeud du cluster HKLM\Cluster\Resources\[GUID]\Parameters\ResourceData -> blob chiffre, format _NNPWD_STRUCTURE contient le mot de passe courant ET le precedent
Le blob et de quoi le lire sont voisins dans la même ruche, sur chaque nœud.
Le détail qui mérite qu’on s’y arrête est le stockage double. La structure _NNPWD_STRUCTURE contient le mot de passe courant et le précédent. La raison est fonctionnelle et parfaitement légitime : la rotation n’est pas atomique à travers les nœuds, il faut donc accepter l’ancien secret pendant la convergence. Les mots de passe de cluster tournent par défaut toutes les heures, ce qui ressemble à une bonne posture. Mais conserver le précédent signifie que la rotation ne ferme pas la fenêtre : elle la maintient ouverte sur deux générations. Un secret capturé juste avant une rotation reste valide après.
Le déchiffrement. Foster identifie NetNameLib::CryptoAccessV2::Decrypt dans clusres.dll comme la fonction qui traite le blob, en créditant le PoC de déchiffrement d’Evan McBroom. Le chemin d’exécution légitime, côté service de cluster, vaut d’être lu pour lui-même : c’est la carte de ce qu’on peut intercepter.
Chaîne d'obtention d'un jeton pour une identité de cluster
NetName::Identity::ObtainNewTokenOperation | +--> NNCommon::NNClusterCrypto::DecryptPassword | lit ResourceData, dechiffre via le conteneur crypto | +--> NetNameLib::CredentialAccess::Logon ouvre une session de logon pour le CNO / VCO le jeton reste vivant dans RHS.exe
RHS.exe conserve des jetons persistants pour CNO et VCO : deux surfaces, le blob au repos et le jeton en mémoire.
Il y a donc deux voies vers la même identité. La voie hors ligne lit le blob et le matériel de clé dans le registre, puis déchiffre. La voie en ligne cible les sessions de logon que RHS.exe maintient déjà. Les deux supposent un accès administrateur local sur un nœud ; aucune des deux n’est une élévation depuis rien.
⚠️ Hypothèse non testée
La voie par vol de jeton dans RHS.exe est une extrapolation de ma part. La publication documente que RHS.exe maintient des sessions persistantes pour CNO et VCO via ObtainNewTokenOperation, mais elle présente l’extraction par le registre — pas le vol de jeton — comme la technique réalisée. Traitez la voie en ligne comme plausible et non établie tant que personne ne l’a démontrée.
Le pivot RBCD. La partie réellement transposable ne part pas d’un nœud compromis. Elle part de l’annuaire. La délégation contrainte basée sur les ressources permet d’écrire l’attribut ms-DS-AllowedToActOnBehalfOfOtherIdentity sur un objet ordinateur que l’on contrôle, puis d’obtenir par S4U2Proxy un ticket de service pour n’importe quel utilisateur. Le prérequis est la permission WriteAccountRestrictions sur les nœuds du cluster, et l’appartenance à Domain Computers suffit à fournir l’objet ordinateur contrôlé.
Ce qui rend la manœuvre particulièrement rentable contre un cluster est énoncé ainsi par Foster : le nœud hébergeant le rôle CNO peut déchiffrer le ticket de service forgé, parce qu’il a accès au mot de passe du CNO stocké dans la base du cluster. Autrement dit, le partage de secret qui rend le basculement transparent rend aussi le ticket forgé acceptable partout. Un ticket qui, face à un service ordinaire, ne vaudrait que contre un hôte précis devient valide face à l’ensemble.
Pourquoi l’outillage habituel casse. C’est le passage le plus utile opérationnellement, et le moins prévisible. Un CNO ou un VCO n’expose que ClusterStorage$ et IPC$. Il n’y a pas d’ADMIN$. Or wmiexec.py et atexec.py d’Impacket écrivent la sortie de commande dans un fichier temporaire sur ADMIN$ avant de la relire. Sans ce partage, les outils échouent — non pas parce que l’authentification a échoué, mais parce que l’étape de récupération de sortie n’a nulle part où écrire. Un opérateur qui n’a pas ce modèle en tête conclura à tort que ses identifiants sont mauvais, et abandonnera un accès qui fonctionnait.
Le service de cluster maintient en outre un handle sur C:\ClusterStorage, ce qui bloque l’écriture arbitraire sur le seul partage restant — une tentative d’écriture directe sur ClusterStorage$ échoue en accès refusé pour cette raison, et non pour un problème de droits. Le contournement documenté consiste à renoncer à la sortie : le drapeau -silentcommand supprime la redirection, et la création de tâche par RPC permet l’exécution sans capture. On exécute à l’aveugle.
La boucle de migration. C’est ici que la technique devient réellement élégante, et c’est la partie qu’un résumé rapide manque. Une fois que l’on exécute dans le contexte du CNO, on n’exécute que sur un nœud : celui qui héberge le rôle à cet instant. Or le propre d’un cluster est que ce rôle se déplace. fustercluck automatise ce déplacement, et l’attaquant s’en sert comme d’un mécanisme de mouvement latéral fourni par la cible elle-même.
Boucle CNO — exécution sur chaque nœud à tour de rôle
# 1. ticket de service forge pour le CNO (via RBCD / S4U2Proxy) # 2. execution sur le noeud qui heberge actuellement le role atexec.py -silentcommand [payload] # 3. identifier le noeud porteur, puis migrer le role fustercluck.py enum_cluster fustercluck.py get_groupstate Cluster\ Group # 4. le role bascule -> rejouer atexec.py pour le noeud suivant atexec.py -silentcommand [payload] # 5. repeter jusqu'a avoir couvert tous les noeuds
Le basculement, concu pour la haute disponibilite, sert de primitive de mouvement lateral.
L’opération ne casse rien et ne déclenche aucune anomalie fonctionnelle : migrer un groupe de ressources est une opération d’administration normale, c’est même ce que l’on fait avant une maintenance. L’attaquant utilise la fonction de basculement pour sa finalité nominale, avec une intention différente. Il n’y a pas d’exploit dans cette étape — seulement l’usage documenté d’une API d’administration par quelqu’un qui a obtenu l’identité qui y donne droit.
Pourquoi le secret est partout : PaxosTag. La réplication de la base de cluster suit un protocole de consensus dont le marqueur est visible et lisible. Le PaxosTag a la forme NextEpochNumber:LastEpochNumber:SequenceNumber. À chaque changement de configuration, le SequenceNumber s’incrémente et une proposition part vers les autres nœuds ; ceux qui constatent un numéro local inférieur acceptent la proposition et répliquent la configuration.
Les mots de passe CNO et VCO voyagent dans ce flux. Foster le formule sans détour : ils sont répliqués à travers le cluster et présents sur chaque nœud, parce que si la ressource bascule vers un autre nœud, les clés doivent avoir basculé avec elle — via des checkpoints stockés en dehors de la base de cluster. Le secret n’est donc pas copié par négligence : il est copié par le mécanisme qui rend la disponibilité possible. Corollaire défensif utile, que Foster mentionne : l’itération du PaxosTag dans la base de cluster est un journal de changements de configuration, donc un endroit où une modification non autorisée laisse une trace.

Quatre chemins vers l'identité de cluster, et ce que chacun coûte réellement.
Limites et arbitrages. Premier point, et il est structurel : il n’y a pas de correctif à attendre. Le partage du secret entre nœuds est ce qui rend le basculement possible. Microsoft ne peut pas le supprimer sans supprimer la fonctionnalité. Ce qui se corrige, ce sont les conditions autour — la délégation, le classement en Tier Zero, la surveillance — pas le mécanisme.
Deuxième point : la voie registre n’est pas une élévation de privilèges. Elle suppose l’administration locale d’un nœud. Sa valeur est celle d’un multiplicateur. La technique elle-même ne franchit aucune frontière ; elle exploite le fait que la frontière n’a jamais existé entre les nœuds. Ce que le cluster porte détermine alors ce que la compromission vaut, et Foster détaille quatre débouchés concrets.
Un cluster ADFS adossé à un groupe de disponibilité SQL permet de forger des assertions SAML — donc de s’authentifier comme n’importe qui auprès de tout service fédéré. Une base SCCM en cluster donne le contrôle de SCCM et, par extension, de l’ensemble de ses clients. Un Exchange Database Availability Group est bâti sur WSFC : compromettre le cluster compromet toutes les boîtes aux lettres. AD CS, enfin, dispose d’une intégration WSFC documentée par Microsoft. La conclusion de Foster est sans nuance : dès que le cluster porte un service Tier Zero, chaque nœud, le CNO et chaque VCO doivent être traités comme des actifs Tier Zero.
Troisième point, une limite d’outillage que Foster signale lui-même : la corrélation d’un VCO vers son CNO exige l’analyse des DACL, et l’énumération des nœuds n’a pas de méthode fiable par le seul annuaire — il faut passer par des requêtes COM, IOXIDResolver et ServerAlive2 servant à énumérer les interfaces réseau. C’est la raison pour laquelle un collector dédié était nécessaire : WSFCHound étend BloodHound via OpenGraph, fustercluck couvre l’énumération et la migration de CNO, ludus_wsfc déploie le laboratoire.
La discrimination par SPN, en revanche, est propre et se fait en lecture seule. Les trois rôles se distinguent sans ambiguïté par leur classe de service.
Discrimination des rôles de cluster par classe de SPN
CNO MSServerCluster <- identifiant unique du cluster VCO MSClusterVirtualServer <- et PAS MSServerCluster Noeud membre MSServerClusterMgmtAPI <- et aucun des deux ci-dessus
Trois classes de SPN, trois roles : de quoi batir un inventaire sans rien ecrire dans l'annuaire.
L’ordre de grandeur justifie l’effort d’inventaire. Foster donne un chiffre issu du parc BloodHound Enterprise : 82 % des environnements observés comportaient au moins un cluster, pour une moyenne de 141 par environnement. Ce n’est pas une technologie de niche que l’on rencontrerait chez un client sur dix.
Quatrième point, et il déplace la responsabilité : la permission qui rend le pivot RBCD possible est parfois recommandée. Foster relève que certaines documentations Microsoft conseillent de déléguer WriteAccountRestrictions à des groupes larges, Domain Computers compris, alors que la recommandation sûre consiste à n’accorder au CNO que le droit de créer des objets ordinateur dans une OU précisément délimitée. La configuration exploitable n’est donc pas nécessairement une erreur d’administrateur ; elle peut être le résultat d’avoir suivi une consigne. C’est ce qui rend l’audit de cette ACL prioritaire sur l’audit d’une négligence supposée.
Cinquième point, et c’est là que le coût défensif est le plus intéressant. Le signal le plus propre est trivial à décrire et rarement collecté : les ressources CNO et VCO peuvent s’authentifier depuis tous les nœuds membres, mais le pool d’adresses sources doit rester statique. Un logon de CNO depuis une adresse hors du pool de nœuds est anormal par construction, sans faux positif structurel. Le corollaire opérationnel est direct : l’usage d’une identité de cluster depuis une machine qui n’est pas un nœud est détectable à coût nul par quiconque a pensé à l’écrire. La seconde détection recommandée — accès à la clé de registre ResourceData en dehors du service de cluster et de ses processus enfants — est plus coûteuse à instrumenter, mais elle frappe la voie hors ligne à la racine.

Partie 03  ·  Deep-dive
Parser avant de vérifier : six failles dans la signature FIT d’U-Boot
Pour savoir quoi hacher, U-Boot doit d’abord interpréter un arbre que l’attaquant contrôle. Six advisories Binarly, aucune faille cryptographique.
Plan de la partie
1

2

3
 BRLY-2026-037 : le NULL, le strcpy, et le garde-fou inversé.
4

5

Binarly a divulgué le 1er juillet six problèmes dans la vérification de signature FIT d’U-Boot, puis publié l’analyse le 9. Le point remarquable de ce lot est négatif : aucune des six n’est une faiblesse cryptographique. Ni RSA, ni SHA, ni la comparaison de condensats. Ce sont toutes des corruptions mémoire dans le code qui prépare la vérification. C’est un cas d’école d’une classe de défaut que la conception du format rend difficile à éviter.
Le format. Un FIT — Flattened Image Tree — est un arbre de périphériques, au même format qu’un DTB, servant de conteneur de démarrage. Il contient un nœud /images (noyau, device tree, ramdisk, avec leurs condensats ou signatures) et un nœud /configurations qui définit des combinaisons d’images bootables.
La décision de conception centrale est que l’on signe une configuration, pas une image isolée. La documentation U-Boot en donne la raison : signer image par image autoriserait les attaques dites mix and match, où l’on recompose une configuration nouvelle à partir d’images légitimement signées issues de versions différentes — un noyau à jour avec un device tree ancien, par exemple. La signature de configuration couvre donc la structure racine de l’image, pour qu’on ne puisse ni ajouter ni retirer de nœud racine, ainsi que les nœuds d’images référencés et leurs sous-nœuds de hash.
Deux propriétés du nœud de signature portent cette mécanique : hashed-nodes, qui enregistre quels nœuds la signature a couverts, et hashed-strings, qui donne l’offset et la longueur, dans la table de chaînes, des chaînes incluses dans la signature. La clé publique vit ailleurs : dans le control FDT d’U-Boot (CONFIG_OF_CONTROL), sous /signature, avec algo, rsa,modulus, rsa,exponent, rsa,r-squared et rsa,n0-inverse.
L’inversion. Voici le détail qui explique les six advisories, et il est explicite dans la documentation U-Boot : U-Boot ne lit pas hashed-nodes à la vérification. Il reconstruit lui-même la liste des régions à hacher, à partir des références de la configuration. Le choix est défendable — faire confiance à une propriété non vérifiée pour décider de ce qu’on vérifie serait circulaire. Mais il a une conséquence mécanique : pour reconstruire cette liste, il faut parcourir l’arbre. L’arbre vient du fichier. Le fichier n’est pas encore vérifié.
Le parcours d’arbre s’exécute donc sur une entrée entièrement hostile, avant toute opération cryptographique. C’est l’inversion parse-then-verify, et elle n’est pas un oubli : on ne peut pas vérifier une signature sans savoir sur quoi elle porte, et on ne peut le savoir qu’en lisant le fichier. La surface d’attaque pré-authentification est le prix structurel du format.
BRLY-2026-037. La fonction fdt_get_name, dans scripts/dtc/libfdt/fdt_ro.c, peut retourner un pointeur nul quand ses contrôles de validation échouent ou dans certaines conditions de version FDT. Ce pointeur est ensuite déréférencé dans fdt_find_regions, dans boot/fdt_region.c, lors d’un strcpy.
boot/fdt_region.c — le chemin vulnérable
name = fdt_get_name(fdt, offset, &len); if (!depth && *name) return -FDT_ERR_BADLAYOUT; if (end - path + 2 + len >= path_len) return -FDT_ERR_NOSPACE; strcpy(end, name);
Deux gardes successifs, et aucun des deux ne tient quand fdt_get_name échoue.
Deux choses cassent en même temps, et c’est ce qui rend le cas intéressant. D’abord, le premier test ne protège pas : il ne déréférence *name que si depth vaut zéro. Dès que la profondeur est non nulle, le test est court-circuité et l’exécution atteint strcpy avec name à NULL — une copie depuis l’adresse 0.
Ensuite, et c’est le point le plus fin, le contrôle de bornes est inversé par le même échec. En cas d’erreur, len reçoit le code d’erreur de fdt_get_name, qui est négatif. L’expression end - path + 2 + len devient donc plus petite que path_len, pas plus grande. Le test de dépassement réussit exactement dans le cas où il devrait échouer. Un garde-fou de taille qui devient permissif quand la fonction en amont a échoué est un motif qu’il vaut la peine de retenir : il apparaît partout où une longueur et un code d’erreur partagent le même entier signé.
Le déclencheur décrit par Binarly est un FIT forgé en version FDT 15 dont les noms de nœuds ne contiennent pas le caractère « / », soumis via la commande fdt checksign. La destination du strcpy est un tampon de pile, d’où la qualification de dépassement de tampon de pile potentiel au-delà du simple déni de service. Versions confirmées : U-Boot v2026.04 et la branche master au commit 38dbe637. Correctif fusionné le 13 juin 2026 (f3d2ff3f). La remédiation tient en une ligne : vérifier que fdt_get_name n’a pas retourné NULL avant de déréférencer.
BRLY-2026-038, la seule qui revendique l’exécution. Elle vit dans la même fonction que 037 et part du même échec de fdt_get_name, mais elle exploite l’autre usage de len. Après la copie, le code avance le curseur d’écriture.
boot/fdt_region.c — l’avance du curseur
strcpy(end, name); end += len; /* len porte le code d'erreur negatif : le curseur RECULE */
Une addition qui devient une soustraction quand la fonction en amont a echoue.
Quand len porte un code d’erreur négatif, le curseur recule au lieu d’avancer. Les écritures suivantes se produisent avant l’adresse de début du tampon, en amont sur la pile — ce qui place l’adresse de retour de la fonction dans la zone atteignable. C’est un primitif d’écriture arrière, et c’est pour cela que Binarly note 038 à 6.8 contre 4.6 pour les autres, en décrivant l’issue comme un contrôle complet de l’équipement par compromission du bootloader.
La remédiation proposée est en deux temps, là où celle de 037 tenait en un : vérifier que fdt_get_name n’a pas retourné NULL, et vérifier que len n’est pas négatif avant de l’utiliser. La seconde moitié est celle qui manquait partout — c’est le même entier signé, réutilisé une ligne plus bas, qui produit deux défauts de nature différente.
Quand l’attaquant choisit ce qui est haché. Les advisories 039 et 041 relèvent d’un troisième motif, et c’est le plus instructif du lot. Il ne s’agit plus d’un pointeur nul, mais d’une taille.
BRLY-2026-039 vise fit_config_check_sig, dans boot/image-fit-sig.c. La fonction récupère la propriété hashed-strings et en prend la seconde valeur, strings[1], comme taille de la région de chaînes — verbatim, sans contrôle. fit_region_make_list la recopie telle quelle dans le tableau region, puis hash_calculate, dans lib/hash-checksum.c, la transmet à sha1_update qui l’interprète comme un entier non signé et lit d’autant. Avec 0xFFFFFFFF, U-Boot lit près de quatre gigaoctets depuis fit + fdt_off_dt_strings(fit), donc bien au-delà de l’image, dans de la mémoire non mappée.
BRLY-2026-041 est le même défaut sur un autre jeu de propriétés. fit_image_get_data(), dans boot/image-fit.c, lit data-position, data-offset et data-size sans les valider contre les bornes de l’image. Ces propriétés sont lues comme des entiers signés — donc des valeurs négatives sont acceptées — puis converties en non signés au moment du calcul de hash.
BRLY-2026-041 — chaîne d'appel jusqu'à l'accès hors limites
fit_image_get_data() lit data-offset / data-size, non valides -> fit_image_check_sig() -> rsa_verify() -> hash_calculate() -> hash_update_sha1() -> lecture hors limites, memoire non mappee
L'acces hors limites se produit a l'interieur de rsa_verify, pas avant lui.
Ces deux cas disent quelque chose de plus fort que « le parser tourne trop tôt ». Ils disent que l’attaquant choisit quelle mémoire est hachée. La fonction de hachage opère sur des régions décrites par le fichier lui-même, avec des tailles et des offsets qu’il fournit, et la signature n’est comparée qu’ensuite. La chaîne d’appel de 041 est explicite sur ce point : rsa_verify apparaît avant l’accès hors limites. La corruption se produit à l’intérieur de l’opération de vérification, pas en amont. Il n’existe donc aucun point du flot où l’on pourrait insérer un contrôle « vérifier d’abord » : la vérification est elle-même le consommateur de l’entrée non fiable.
BRLY-2026-042. Le dernier cas est d’une autre nature et vaut pour l’ironie autant que pour la technique. La fonction fdt_check_no_at(), dans boot/image-fit.c, existe pour refuser les noms de nœuds contenant un « @ », c’est-à-dire pour éliminer l’ambiguïté d’adresse d’unité. C’est une contre-mesure. Elle parcourt l’arbre récursivement, sans borne.
boot/image-fit.c — fdt_check_no_at()
static int fdt_check_no_at(const void *fit, int parent) { const char *name; int node; int ret; name = fdt_get_name(fit, parent, NULL); if (!name || strchr(name, '@')) return -EADDRNOTAVAIL; fdt_for_each_subnode(node, fit, parent) { ret = fdt_check_no_at(fit, node); if (ret) return ret; } return 0; }
Appelée depuis fit_check_format() (boot/image-fit.c:1699) dès que CONFIG_IS_ENABLED(FIT_SIGNATURE).
Le contrôle en amont, fdt_check_full(), ne borne la profondeur qu’à INT_MAX — 2 147 483 647. Autant dire rien. Binarly donne l’arithmétique qui rend la situation déterministe plutôt que fortuite : chaque appel récursif consomme 16 octets de pile, alors qu’un niveau d’imbrication supplémentaire ne coûte que 12 octets dans le fichier. Le rapport est défavorable par construction — le fichier grossit moins vite que la pile qu’il consomme — ce qui garantit le débordement même sur une plateforme disposant de RAM confortable. Le PoC utilise 500 000 sous-nœuds vides imbriqués et produit une faute de segmentation quand le pointeur de pile atteint une page non mappée.
La correction proposée est instructive : introduire un compteur de profondeur et rejeter au-delà d’une limite raisonnable, en réutilisant FDT_MAX_DEPTH, déjà défini à 32 dans boot/fdt_region.c. La constante existait donc déjà, dans le fichier voisin, pour exactement ce problème. Correctif fusionné le 12 juin 2026 (9e0d2fb4).

Cinq des six advisories sont des impacts de disponibilité. BRLY-2026-038 est l'exception, et c'est elle qui porte le poids du lot.
Ce que disent les scores, et ce que la presse en a fait. Cinq des six advisories partagent le vecteur AV:P/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H, soit 4.6, Medium. Il faut lire ce vecteur en entier. AV:P signifie vecteur physique : il faut pouvoir présenter le FIT à l’équipement. C:N/I:N signifie que Binarly ne revendique, pour ces cinq-là, ni perte de confidentialité ni perte d’intégrité. A:H porte tout le score : l’impact revendiqué est la disponibilité.
L’exception change la lecture d’ensemble, et c’est elle qu’il faut retenir. BRLY-2026-038, à 6.8, revendique bien l’exécution de code au niveau du bootloader et un contrôle complet de l’équipement. La couverture presse a titré sur des bugs critiques minant le démarrage sécurisé de millions d’équipements : cette formulation est défendable pour 038 seule, et ne l’est pour aucune des cinq autres.
Le décalage n’est donc pas dans le fond, mais dans la généralisation. Un lot de six est résumé par le pire de ses membres, et le lecteur qui n’ouvre pas les advisories en retient que six failles cassent le secure boot — quand cinq d’entre elles font planter un équipement auquel on a déjà un accès physique. Le réflexe utile vaut dans les deux sens : le vecteur CVSS posé par un chercheur est une déclaration de ce qu’il a établi, et il est plus fiable que le résumé qui en est fait, y compris quand ce résumé minimise. Le chiffre de « millions d’équipements », lui, n’apparaît dans aucune des six advisories.
Limites et arbitrages. Aucun identifiant CVE n’était attribué au moment de la publication ; les références sont les identifiants BRLY. Pour du suivi de parc, c’est un handicap concret : un scanner indexé sur CVE ne verra rien.
L’intérêt offensif réel n’est pas dans le score. Il est dans le contexte d’usage. AV:P est une limite sévère pour un serveur en centre de données et n’en est pratiquement pas une pour du matériel embarqué, où l’accès physique est le point de départ normal du travail. Dans ce cadre, le FIT est une entrée non signée vers du code s’exécutant dans le contexte du bootloader — donc avant le noyau, donc avant toute mesure de sécurité portée par le système. Et pour les cinq advisories de disponibilité, un plantage est déjà un résultat exploitable dans une campagne de glitching, où l’objectif est souvent d’amener la cible dans un état non prévu plutôt que d’obtenir directement l’exécution.
⚠️ Hypothèse non testée
Pour BRLY-2026-037, le passage du déni de service à l’exécution suppose que la page zéro soit mappée et que son contenu soit influençable. Binarly écrit « potential » et ne publie pas de PoC d’exécution. J’ai lu ailleurs que la page zéro est fréquemment mappée en contexte bootloader sur plateformes ARM, ce qui rendrait la condition réaliste, mais je ne l’ai pas vérifié et ce n’est pas dans l’advisory. Cette réserve ne vaut pas pour BRLY-2026-038, dont l’écriture arrière sur la pile est décrite par Binarly comme aboutissant à l’exécution sans condition de ce type.
Enfin, la portée temporelle est le vrai sujet. Les chemins de code concernés sont présents depuis la version v2013.07, ce qui représente plus de cinquante versions stables, sans compter les forks vendeurs. Or U-Boot embarqué est presque toujours consommé sous forme de fork : un SoC de 2016 embarque une branche figée par son fondeur, qui ne recevra jamais f3d2ff3f. Le correctif amont existe depuis le 13 juin ; sa propagation est un problème différent, et c’est précisément ce que le volet méthodologique de Binarly — extraire et identifier les U-Boot à l’échelle, cité en partie 01 — cherche à rendre mesurable.

SonicWall publie ses correctifs le 14 juillet ; CISA inscrit CVE-2026-15409 et CVE-2026-15410 au KEV le même jour. Volexity publie son analyse le 17, avec des règles YARA dans son dépôt public de renseignement. L’infrastructure d’attaque compte plus de 200 adresses IP, incluant des nœuds ExpressVPN et Mullvad ainsi que des adresses directes telles que 108.205.8.173, 147.45.51.19 et 202.8.105.201.
Jugement technique. Ce qui est réellement nouveau ici tient en une étape : l’injection d’agents Java dans la JVM d’une appliance pour réécrire le comportement de classes JSP déjà compilées. Cela supprime l’artefact qui reste, en pratique, le premier signal de compromission d’un serveur web : un fichier de webshell sur le disque. Une recherche de fichiers .jsp récents ne trouve rien, un contrôle d’intégrité du webroot ne trouve rien, et les deux points d’entrée sont des URL d’API parfaitement banales, /__api__/login et /__api__/logout, redirigées en interne vers des pages d’erreur.
Le reste est du répertoire public. La SSRF, le path traversal, tcpdump sur 389, le binaire setuid : rien qui n’ait vingt ans. ORANGETAIL est décrit comme un webshell de type Behinder, c’est-à-dire un dérivé d’un outil public. Et le choix cryptographique est médiocre pour qui sait ce qu’il fait : AES-128-ECB avec une clé codée en dur cumule deux faiblesses indépendantes — le mode ECB laisse apparaître des motifs sur du trafic structuré, et une clé codée en dur est extractible du JAR par quiconque le récupère. Un défenseur qui obtient l’échantillon peut déchiffrer le trafic capturé. C’est une décision d’opérateur, pas une contrainte technique.
Le maillon faible est admin:admin. La SSRF donne le tunnel, mais un tunnel vers un service qui refuse l’authentification ne mène nulle part. Toute la chaîne repose sur le fait qu’un CouchDB lié à 127.0.0.1 conservait des identifiants par défaut. L’hypothèse implicite du constructeur est que « lié à la boucle locale » équivaut à « authentifié ». La même hypothèse apparaît deux fois de plus dans ce numéro : le nœud de cluster qui fait confiance à ses pairs parce qu’ils partagent son secret, et le bootloader qui interprète un arbre avant d’en vérifier la signature. Trois architectures, une seule erreur : une frontière de confiance qui n’est jamais évaluée, parce que l’on suppose que personne ne peut se tenir du mauvais côté.
Où la chaîne aurait dû être vue. À l’étape 1, et sans instrumentation particulière. Une requête /wsproxy portant host=0.0.0.0 et répondue par un code 101 est anormale par nature : elle est écrite en clair dans /var/log/aventail/extraweb_access.log. Un code 101 sur un endpoint de proxy est un événement rare et facile à compter. Second raté, plus net encore : la ligne running hotfix removal for:../../../../../tmp/1234.sh dans ctrl-service.log est un path traversal littéral, en clair, dans un journal applicatif — six jours avant la divulgation éditeur. La télémétrie existait, elle était lisible sans outil, et elle n’a pas été exploitée. C’est le constat le plus coûteux de cette autopsie : la détection ne demandait pas de capacité supplémentaire, seulement une lecture.
Sur la discipline opérationnelle, enfin, le contraste vaut d’être noté. Plus de 200 adresses sources, ExpressVPN et Mullvad pour l’anonymisation, un webshell conditionné à un User-Agent pour éviter le scan opportuniste : l’infrastructure est soignée. Mais les journaux de mouvement latéral ont laissé fuiter des noms d’hôte de postes attaquants — DESKTOP-5P0TSCP, DESKTOP-IC3C80F, DESKTOP-KRLUI3J et, sans ambiguïté, KALI. Deux cents nœuds VPN et une machine nommée KALI dans les journaux de la victime : l’anonymisation réseau ne compense pas l’hygiène du poste de travail.

⚠️ Hypothèse non testée
Observation qui m’est propre et que la publication n’énonce pas : les fichiers de persistance sont datés du 22 juin, alors que les traces d’exploitation de /wsproxy dans les journaux sont du 28. La compromission précède donc de six jours l’activité journalisée. Deux lectures sont possibles — une première intrusion par une voie non journalisée ou dont les journaux avaient tourné, ou une ré-entrée le 28 sur une appliance déjà tenue. Je ne dispose d’aucun élément pour trancher, et l’étape 1 ci-dessus ne doit donc pas être lue comme le vecteur d’accès initial établi du 22 juin.
