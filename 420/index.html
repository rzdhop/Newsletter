› Check Point détaille quatre corruptions mémoire dans workerd, le runtime de Cloudflare Workers et de Code Mode. Le point commun n'est pas le bug : c'est que la glue C++ de JSG alloue sur le tas tcmalloc du processus, hors de la cage V8 et hors des clés de protection mémoire. La frontière d'isolation existe, elle ne passe simplement pas là où l'exploitation a lieu.

Partie 02  ·  Deep-dive
La cage est ailleurs : corruption mémoire dans workerd
Des corruptions mémoire dans le runtime de Cloudflare Workers, toutes sur le tas que ni le bac à sable V8 ni les clés de protection mémoire ne couvrent.
Plan
1
 Le modèle : plusieurs locataires dans un processus, une frontière logicielle
2
 Où vit réellement le code exploitable : JSG et le tas tcmalloc
3
 Quatre défauts, quatre invariants : URLPattern, node:zlib, HTMLRewriter, l'authorizer SQLite
4
 De la lecture hors limites à la lecture arbitraire : fabriquer un kj::String
5
 Limites et contreparties : ce que la démonstration établit, et sous quelle configuration
Check Point publie le 6 août une série de corruptions mémoire dans workerd, le runtime qui exécute Cloudflare Workers et, depuis peu, Cloudflare Code Mode. Le n°416 l'avait signalé en partie 01 comme un candidat sérieux ; il l'était. Ce qui rend le travail intéressant n'est aucun des bugs pris isolément — un désaccord de comptage ici, un pointeur pendouillant là — mais le fait qu'ils tombent tous au même endroit, et que cet endroit est précisément celui que l'architecture de sécurité ne couvre pas.
Un mot sur Code Mode, parce que c'est ce qui déplace le curseur. L'argument habituel pour tolérer une frontière logicielle est que le code déployé sur Workers est celui d'un client identifié, qui a signé un contrat et qui a peu d'intérêt à faire tomber la plateforme. Code Mode fait exécuter dans le même runtime du code produit par un modèle de langage à partir d'instructions arbitraires. Le locataire n'est plus une entreprise : c'est une génération de texte. L'hypothèse « le code déployé est globalement bien intentionné », qui n'était écrite nulle part mais qui portait une part du raisonnement, cesse simplement de tenir — et c'est le même tas tcmalloc en dessous.
Le modèle d'exécution de Workers est connu et assumé : many tenants, one process. Là où une plateforme classique donne un conteneur ou une machine virtuelle par client, Workers donne un isolate V8. L'isolation est réalisée au niveau du runtime de langage, pas au niveau du système : c'est une frontière logicielle à l'intérieur d'un unique espace d'adressage. Le compromis est explicite et il est bon — c'est ce qui permet un démarrage à froid en unités de millisecondes plutôt qu'en centaines. Mais il déplace toute la charge de la preuve sur la robustesse du runtime, et il fait d'une corruption mémoire dans ce runtime un problème de multi-location, pas seulement un problème de stabilité.
Pour tenir la promesse, deux mécanismes sont invoqués d'habitude. Le premier est le bac à sable V8, la « cage » : une région réservée à l'intérieur de laquelle les pointeurs du tas V8 sont exprimés en décalages plutôt qu'en adresses, de sorte qu'une corruption du tas JavaScript ne puisse pas désigner de mémoire arbitraire. Le second est le marquage de pages par clés de protection mémoire. Les deux sont réels. Le problème est leur périmètre, et la documentation de V8 le dit elle-même sans détour : le bac à sable couvre le tas V8, le modèle d'attaquant supposé est « un attaquant qui lit et écrit arbitrairement à l'intérieur du bac à sable », l'objectif étant d'empêcher la corruption à l'extérieur. La même page ajoute qu'il reste « un certain nombre de problèmes à résoudre avant que ce soit une frontière de sécurité solide » [13].
Voilà le point d'articulation de toute la recherche. Pour offrir les API Node, workerd n'appelle pas Node : il en réimplémente une large part en C++, à travers une couche de liaison appelée JSG, pour JavaScript Glue. Les objets natifs que cette couche manipule — les structures zlib, les itérateurs de lol-html, les tampons intermédiaires — ne sont pas alloués dans le tas V8. Ils sont alloués sur le tas tcmalloc du processus. Ce tas n'est ni dans la cage, ni couvert par les clés de protection mémoire. Cloudflare l'a confirmé aux auteurs en ces termes. Autrement dit : la frontière d'isolation existe, elle est correctement implémentée, et l'exploitation a lieu un étage en dessous.
Le premier défaut illustre le mécanisme à peu de frais. L'API URLPattern compile un motif en expression régulière et rend les groupes capturés associés à leurs noms. Deux composants comptent les groupes : le parseur de workerd, qui construit la liste des noms, et V8, qui compile effectivement la regex. Sur un motif à groupe imbriqué du type (ab(cde)), le parseur de workerd ne retient que le groupe externe, tandis que V8 en compte deux. La boucle de restitution itère sur le compte rapporté par V8 et indexe la liste construite par l'autre : au second tour, elle lit hors limites.
URLPattern — deux comptages qui divergent
// Motif : un groupe de capture imbrique // (ab(cde)) // // V8 compile la regex et compte DEUX groupes : // [1] = "abcde" groupe externe // [2] = "cde" groupe interne // // Le parseur d'URLPattern de workerd ne retient que // le groupe externe : nameList.size() == 1 for (size_t i = 0; i < v8Groups.size(); ++i) { // 2 tours auto& name = nameList[i]; // i == 1 : hors limites result.set(name, v8Groups[i]); }
Forme adaptée de l'analyse Check Point [11]. Le nombre d'itérations vient de V8, l'indexation porte sur une liste construite par un autre parseur. Ce qui est lu au-delà de nameList est ce qui suit dans le tas tcmalloc — donc de la mémoire du processus, partagée avec les autres locataires.
Une lecture hors limites d'un élément ne vaut pas grand-chose en soi. Sa valeur vient de ce que la structure lue est un objet kj::String — pointeur et longueur. En plaçant à l'endroit voulu du tas une paire pointeur/longueur fabriquée, on obtient une lecture arbitraire : le moteur restitue le contenu de l'adresse choisie comme s'il s'agissait d'un nom de groupe capturé. C'est le passage habituel d'un défaut spatial borné à une primitive générique, et il ne réussit ici que parce que la cible vit hors de la cage, là où un pointeur est encore une adresse.
Le deuxième défaut est un use-after-free dans la réimplémentation de node:zlib, et c'est celui que Cloudflare classe Critical. La couche de liaison recopie les pointeurs bruts des tampons JavaScript dans la structure z_stream de zlib, notamment next_out. Le chemin d'écriture rend la main sans jamais réinitialiser ce champ. Côté JavaScript le tampon peut ensuite être libéré ou réaffecté ; côté natif le pointeur reste en place. Il suffit alors d'appeler deflateParams(), qui n'exige pas de nouveau tampon : si un Z_NO_FLUSH antérieur a laissé des données en attente, la fonction vide le reliquat à travers next_out.
node:zlib — next_out survit à l'appel
// setBuffers() recopie les pointeurs bruts du tampon JS // dans la structure z_stream : stream.next_out = outBuffer.begin(); stream.avail_out = outBuffer.size(); // write() rend la main SANS remettre next_out a nullptr. // Cote JS, outBuffer peut desormais etre libere ou reaffecte. // Cote natif, stream.next_out pointe toujours dessus. // deflateParams() n'attend pas de nouveau tampon : si un // Z_NO_FLUSH anterieur a laisse des octets en attente, il // les ecrit a travers next_out — dans la memoire liberee. deflateParams(&stream, level, strategy);
Forme adaptée de l'analyse Check Point [11]. La primitive n'est pas une lecture mais une écriture, à une adresse du tas tcmalloc susceptible d'avoir été réattribuée entre-temps.
Le troisième suit le même patron sur un composant différent : l'itérateur d'attributs de HTMLRewriter, construit au-dessus des liaisons C++ de lol-html, conserve un pointeur brut vers le tableau d'attributs de l'élément. Un appel à setAttribute() peut provoquer la réallocation de ce tableau, et l'itérateur continue de pointer vers l'ancienne zone. C'est l'invalidation d'itérateur canonique du C++, transposée dans une API exposée à du code non fiable : Cloudflare le classe également Critical.
Le quatrième n'est pas une corruption mémoire et c'est ce qui le rend instructif. Le stockage des Durable Objects expose deux vues sur la même base SQLite : une API clé/valeur, qui sérialise par clonage structuré, et une API SQL brute. Un authorizer SQLite est chargé d'interdire au SQL de toucher aux tables internes préfixées _cf_. Il valide les noms de tables référencés par une requête — mais pas le nom de destination d'un renommage. Rien n'empêche donc de créer une table ordinaire sous un nom autorisé, de la remplir d'octets choisis, puis de faire :
Durable Objects — le nom de destination n'est pas contrôlé
-- Interdit : l'authorizer voit la reference a _cf_KV SELECT * FROM _cf_KV; -- Autorise : la table referencee porte un nom permis, -- et le nom de DESTINATION n'est pas soumis au controle CREATE TABLE scratch (key TEXT, value BLOB); INSERT INTO scratch VALUES ('k', x'...'); ALTER TABLE scratch RENAME TO _cf_KV; -- Ensuite, cote API cle/valeur : -- storage.get('k') -- alimente les deserialiseurs internes de workerd avec -- des octets entierement choisis par le locataire.
D'après [11]. Le contrôle porte sur la mauvaise moitié de l'instruction&nbsp;; ce que l'API clé/valeur croit relire, c'est sa propre table interne.

Quatre défauts, un seul dénominateur commun : la cible vit sur le tas tcmalloc, hors cage et hors clés de protection mémoire.
Une précision de comptage avant de conclure, parce qu'elle change ce qu'on peut affirmer : l'article annonce cinq problèmes mais n'en détaille pas cinq au même niveau, et son propre décompte des vulnérabilités formellement remontées à Cloudflare est de trois. Les quatre décrits ci-dessus sont ceux dont le mécanisme est établi dans le texte. Nous n'attribuons pas de cinquième défaut faute de pouvoir dire lequel ; c'est une lacune de notre lecture autant que du billet.
Limites et contreparties. C'est la partie qui décide de ce que vaut réellement cette recherche, et les auteurs sont honnêtes sur les quatre points qui comptent. Premièrement, la chaîne allant du use-after-free zlib à l'exécution de code natif a été construite contre un workerd auto-hébergé, compilé avec le bac à sable V8 désactivé ; les auteurs précisent que la technique employée ne fonctionnerait pas telle quelle avec la cage active. Deuxièmement, la lecture cross-tenant n'a pas été testée en production, et pour une raison qui est elle-même un enseignement : un exploit mémoire qui plante le processus emporterait les autres locataires. Troisièmement, le chemin authorizer → désérialisation n'a pas été poursuivi jusqu'à l'exécution — il est décrit comme une surface d'attaque très forte, pas comme un résultat. Quatrièmement, la variante d'URLPattern déployée en production ne déclenche pas le défaut ; seule la version standard adossée à Ada le reproduit.
À quoi s'ajoute une nuance que le dépôt workerd énonce lui-même, et qu'il faut lire avant de conclure quoi que ce soit sur Cloudflare : « workerd tente d'isoler chaque Worker […] mais workerd seul ne contient pas de défense en profondeur adaptée face à d'éventuels bugs d'implémentation », et l'exécution de code non fiable y est explicitement renvoyée à une machine virtuelle [12]. La production de Cloudflare empile d'autres couches. Ce qui est démontré ici, ce n'est donc pas que Workers est ouvert ; c'est que la couche runtime, prise seule, ne tient pas — ce que l'éditeur du runtime écrit noir sur blanc, et ce que la plupart des déploiements auto-hébergés ignorent en installant workerd comme serveur applicatif.
⚠️ Hypothèse non testée
Les extraits de code ci-dessus sont des reconstructions de forme destinées à rendre le mécanisme lisible, pas le code de workerd. Ils suivent la description de Check Point ; les noms de champs (next_out, avail_out, nameList) sont réels, l'agencement des appels est illustratif. Par ailleurs, l'affirmation selon laquelle le contenu écrit via next_out est contrôlable par l'attaquant à travers le flux compressé est une inférence de notre part sur le fonctionnement de deflate : l'article établit la primitive d'écriture et son classement Critical, pas le degré de contrôle sur les octets écrits.
Ce que cette architecture coûte à un défenseur mérite une ligne, parce que c'est l'angle le moins traité. Dans un modèle un-processus-par-client, un plantage, une allocation anormale ou une lecture hors limites portent une étiquette : le PID désigne le responsable. Ici, les milliers d'isolates partagent un espace d'adressage et un tas ; la télémétrie de l'hôte voit un processus qui alloue, se corrompt et éventuellement meurt, sans rien qui rattache l'événement à un locataire. L'attribution doit donc être reconstruite au niveau applicatif, par le runtime lui-même — c'est-à-dire par le composant dont on est précisément en train de suspecter l'intégrité. C'est la contrepartie structurelle du démarrage à froid en millisecondes, et elle ne se corrige pas par un correctif.
Reste la question de suivi. Au moment de la publication, aucun CVE n'a été assigné. Les Workers gérés ont été corrigés en production, et les déploiements auto-hébergés doivent passer en workerd v1.20260619.1. Pour qui exploite workerd hors Cloudflare — et le dépôt liste ce cas comme un usage prévu — l'absence d'identifiant CVE signifie qu'aucun scanner de dépendances ne signalera la version vulnérable. C'est le genre de détail qui décide de la vitesse de correction d'un parc, indépendamment de la qualité de la recherche.

Quatre contrôles, zéro vérification : CVE-2026-55040 dans SharePoint
Un jeton entièrement fabriqué traverse quatre validations successives, parce qu'aucune des quatre ne fait ce que son nom annonce.
Plan

2

3

4

5

Rapid7 publie le 11 août l'analyse de cause racine de CVE-2026-55040, un contournement d'authentification non authentifié dans SharePoint Server. Microsoft l'a corrigé au Patch Tuesday de juillet et le classe sobrement en « Security Feature Bypass » ; la description interne est plus parlante : weak authentication […] allows an unauthorized attacker to bypass a security feature over a network, avec cette précision dans la FAQ — « la fonctionnalité d'authentification peut être contournée car cette vulnérabilité permet l'usurpation d'identité » [15]. CVSS 9.1, AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:N. L'intérêt du billet n'est pas l'existence du bug : c'est qu'il montre quatre contrôles distincts qui ressemblent tous à une vérification et dont pas un seul ne vérifie.
Le contexte est l'authentification serveur à serveur. SharePoint doit pouvoir accepter un jeton émis par un tiers de confiance — un service de jetons de sécurité — affirmant « j'ai authentifié tel utilisateur, agis en son nom ». Le mécanisme repose sur un jeton extérieur qui transporte un jeton acteur imbriqué ; c'est le jeton acteur qui porte l'identité usurpable, et c'est donc sa signature qui constitue toute la sécurité du dispositif. Le design est classique et sain sur le papier. Toute la question est de savoir si la signature est effectivement contrôlée.
Le premier défaut est le plus direct. Dans SPJsonWebSecurityTokenHandlerV2.ValidateToken(), le code positionne RequireSignedTokens = false sur les paramètres de validation. La bibliothèque JWT sous-jacente cesse alors d'exiger une signature sur le jeton extérieur, qui peut donc arriver en alg: none. Pris seul, ce serait déjà discutable ; l'argument de défense serait que la vraie identité est dans le jeton acteur, lui signé. C'est là que les trois suivants interviennent.
Le deuxième porte sur la résolution de la clé. SPJsonWebSecurityBaseTokenHandlerV2.GetSigningKeyIdentifier() lit la valeur x5t — l'empreinte du certificat — directement dans l'en-tête du jeton acteur, la décode via SPBase64UrlEncoder.DecodeBytes(), et la passe à SPIssuerTokenResolver.TryResolveTokenCore() qui la résout en certificat. Autrement dit : c'est le jeton fourni par l'attaquant qui désigne la clé avec laquelle il sera contrôlé. Un en-tête n'est pas une donnée de confiance, il fait partie du message. Et la formule que retient Rapid7 est sans ambiguïté : à aucun moment de ce flux la signature du jeton acteur n'est vérifiée cryptographiquement.
Reste à savoir quelle empreinte fournir. Elle est publique : une requête non authentifiée sur /_layouts/15/metadata/json/1 renvoie le certificat x509 du STS de l'instance dans sa réponse JSON. L'attaquant récupère donc le certificat de signature de la cible elle-même, en calcule l'empreinte, et la place dans x5t. Le serveur se retrouve à résoudre sa propre clé — ce qui est cohérent, puisqu'il ne s'en servira de toute façon pas.
Forme du jeton — l'en-tête choisit la clé, la signature n'est pas contrôlée
// Jeton EXTERIEUR : la signature n'est plus exigee // RequireSignedTokens = false -> alg: none accepte { "alg": "none", "typ": "JWT" } { "aud": "<principal SharePoint>/<hote>@<realm>", "iss": "<emetteur quelconque>", "actortoken": "<jeton acteur ci-dessous>" } // Jeton ACTEUR : c'est lui qui porte l'identite { "alg": "RS256", "x5t": "<empreinte du certificat STS de la cible>" } { "nameid": "<SID ou UPN de l'utilisateur vise>", ... } // partie signature : une chaine non vide quelconque
Forme illustrative d'après [14]&nbsp;; les valeurs exactes des revendications ne sont pas reproduites ici. Le point est structurel&nbsp;: l'en-tête du jeton acteur désigne la clé, et la partie signature n'a besoin que d'exister.
Le troisième défaut ferme la porte de secours. La méthode ValidateIssuer(X509SecurityToken, string) interroge GetProviderBySigningCertificate() pour retrouver l'émetteur associé au certificat. Quand ce certificat est absent de TrustedSecurityTokenServices — c'est-à-dire quand il n'est enregistré comme émetteur de confiance nulle part — la méthode ne lève pas de SecurityTokenException : elle retourne, purement et simplement. L'émetteur inconnu est donc accepté sans condition. Le contrôle qui devait rejeter l'inattendu est celui qui l'entérine.
Le quatrième est le plus court à décrire et le plus difficile à croire. GetTokenSignature() extrait la partie signature du JWT et exige qu'elle soit non vide. C'est tout. Aucune vérification cryptographique, aucune comparaison contre une clé, aucun contrôle d'algorithme. Une chaîne arbitraire passe. Le nom de la méthode annonce une signature ; son contrat réel est une contrainte de présence.
Les quatre contrôles, dans l'ordre où ils échouent
// 1. La bibliotheque n'exigera plus de signature val.RequireSignedTokens = false; // 2. La cle est designee par l'en-tete du jeton lui-meme kid = GetSigningKeyIdentifier(actorToken); // lit x5t, sans controle cert = TryResolveTokenCore(kid); // -> certificat STS de la cible // 3. Certificat absent de TrustedSecurityTokenServices ? if (GetProviderBySigningCertificate(cert) == null) return; // retour silencieux, au lieu de lever // 4. "Verification" de la signature sig = GetTokenSignature(actorToken); // exigence : sig non vide. Rien d'autre.
Reconstruction de la logique décrite dans [14]. Chacune de ces quatre étapes existe, porte un nom de contrôle de sécurité, et laisse passer un jeton entièrement fabriqué.
Contrôle Méthode Ce qu'il a l'air de faire Ce qu'il fait
Exigence de signature ValidateToken() Imposer un jeton signé RequireSignedTokens à false&nbsp;: alg none accepté
Résolution de clé GetSigningKeyIdentifier() / TryResolveTokenCore() Retrouver la clé de l'émetteur Utilise l'empreinte x5t fournie par le jeton
Validation d'émetteur ValidateIssuer(X509SecurityToken, string) Rejeter un émetteur non enregistré Retourne sans lever si le certificat est inconnu

Quatre contrôles indépendants. Aucun ne doit être contourné : il suffit de les emprunter dans l'ordre prévu.
Le résultat opérationnel est l'usurpation : la revendication nameid du jeton acteur est fixée à l'identité visée, et SharePoint traite la requête comme provenant de cet utilisateur, administrateurs de collection compris. C'est ici qu'apparaît le seul facteur réellement limitant, et il mérite qu'on s'y arrête parce qu'il détermine si l'exploitation est un script ou un travail. L'attaquant doit connaître à l'avance un SID Windows valide ou un UPN de la cible. Les auteurs sont clairs sur le classement des deux voies : obtenir un SID valide est plus fiable en scénario automatisé — en interrogeant le contrôleur de domaine du serveur SharePoint via SMB — que de deviner des UPN par force brute. Ce qui replace la vulnérabilité à sa juste place : non authentifiée sur SharePoint, oui ; mais l'exploitation confortable suppose une visibilité réseau sur l'annuaire, donc une position interne ou un périmètre mal découpé. Depuis Internet, sans SID, il reste l'énumération d'UPN.
Il vaut la peine de nommer le patron, parce qu'il se répète. Les quatre défauts sont des fail-open : à chaque point de décision, le cas « je ne sais pas » est traité comme « c'est bon ». Certificat introuvable dans les émetteurs de confiance : on retourne. Signature présente mais invérifiable : on se contente de sa présence. Signature absente : on a désactivé l'exigence en amont. Aucune de ces décisions n'est absurde prise isolément — chacune évite une régression pour un déploiement légitime mal configuré, et c'est précisément pour ça qu'elles ont été écrites ainsi. Le défaut n'est pas dans une ligne, il est dans la direction par défaut : quatre développeurs différents, à quatre endroits différents, ont choisi de ne pas casser le cas incertain.
Avant les limites, une remarque de traque, parce que le mécanisme en offre une gratuitement. L'étape de reconnaissance n'est pas discrète : pour construire son jeton, l'attaquant doit d'abord récupérer le certificat STS, et il le fait par une requête non authentifiée sur /_layouts/15/metadata/json/1. C'est une URL que personne n'atteint en naviguant, qui n'apparaît pas dans un parcours utilisateur normal, et qui est journalisée par IIS comme n'importe quelle autre. Un décompte des accès à ce chemin depuis des sources externes, sur les trente derniers jours, coûte une requête et donne une réponse exploitable : soit personne ne l'a demandé, soit quelqu'un préparait un jeton. C'est un des rares cas où l'étape la moins technique de la chaîne est aussi la plus visible.
Limites et contreparties. D'abord la portée annoncée : le billet ne nomme qu'une version précise de SharePoint Server Subscription Edition, tandis que l'avis Microsoft couvre plus large — la FAQ traite explicitement le cas de SharePoint Server 2016 et Enterprise Server 2016, qui partagent le même KB [15]. Ne pas conclure d'une version citée dans un article de recherche à un périmètre de vulnérabilité. Ensuite les métriques temporelles : au moment de la publication de l'avis, Microsoft indiquait Publicly Disclosed:No; Exploited:No avec la mention Exploitation More Likely, et un vecteur temporel E:U — code d'exploitation non prouvé. Cette dernière valeur est celle qui vieillit le plus mal : elle décrivait un état du monde, pas une propriété du bug.
Le calendrier lui-même est un objet d'analyse. La vulnérabilité est divulguée le 14 juillet avec le correctif ; l'analyse de cause racine sort le 11 août, quatre semaines plus tard. Cet intervalle est une décision éditoriale de l'équipe qui a trouvé le bug, et il a une conséquence directe : pendant quatre semaines, un parc non corrigé était exposé à un défaut dont la difficulté de rétro-ingénierie constituait la seule protection résiduelle. Depuis le 11 août, cette protection n'existe plus. Pour un administrateur SharePoint on-premise, la date à retenir n'est donc pas juillet mais avant-hier.
Enfin la remarque qui devrait décider de la priorité de correction : les auteurs signalent que ce contournement d'authentification peut se chaîner avec une seconde vulnérabilité d'exécution de code encore non corrigée, l'ensemble donnant une exécution de code à distance non authentifiée. Prise isolément, CVE-2026-55040 est cotée A:N — aucun impact sur la disponibilité — ce qui la maintient à 9.1 plutôt qu'à 10.0 et la fait passer, dans beaucoup de files de traitement, derrière des vulnérabilités plus bruyantes. Chaînée, elle est la moitié d'une RCE pré-authentification sur un serveur qui contient, par construction, les documents de l'entreprise.

Deux réserves. Le pseudo-code ci-dessus est une reconstruction de la logique décrite par Rapid7, pas du code SharePoint décompilé : les noms de méthodes et de propriétés sont ceux de l'article, l'enchaînement est illustratif. Par ailleurs, la seconde vulnérabilité d'exécution de code évoquée par les auteurs n'est ni identifiée ni détaillée dans le billet ; nous la mentionnons parce qu'elle change l'évaluation du risque, mais nous ne pouvons pas la caractériser, et rien ici n'établit qu'elle soit exploitable dans les mêmes conditions. Enfin, la piste de traque sur /_layouts/15/metadata/json/1 est notre raisonnement à partir du mécanisme décrit, pas une recommandation de Rapid7 ni une détection validée en production ; l'endpoint peut être sollicité légitimement par des intégrations serveur à serveur, et un décompte non nul n'est pas à lui seul un signe de compromission.

Le maillon faible. Il n'est pas dans le noyau, il est deux phases plus tôt. L'exploitation d'AFD.sys est la partie la plus coûteuse à produire et la moins observable une fois FudModule chargé ; le sideloading, lui, est bruyant par construction. À quelle phase cela aurait dû être arrêté. La réponse est contrainte par la chaîne elle-même, et c'est ce qui rend le cas intéressant. La télémétrie qui existait et n'a pas servi. Le rapport apporte ici une nuance qu'il faut lire correctement. L'étape dédiée à la neutralisation de la surveillance de MsMpEng.exe, présente dans des variantes antérieures, n'est plus référencée par du code exécutable dans cet échantillon : Defender est aveuglé, mais par le moteur générique de suppression des produits de sécurité, pas par un traitement spécifique. Cela signifie que les protections Defender restaient en place et n'étaient pas ciblées nommément — un angle mort d'attaquant, pas un angle mort de défenseur, et une piste concrète pour qui reconstruit l'incident a posteriori.
Une contradiction dans l'avis lui-même. Elle vaut d'être signalée parce qu'elle a des conséquences opérationnelles. Le dossier MSRC de CVE-2026-68820 porte, dans le même document, un champ d'état d'exploitation qui indique Exploited:Yes avec la mention Exploitation Detected, et un vecteur CVSS temporel qui porte E:U — code d'exploitation non prouvé. Une chaîne de priorisation qui lit le vecteur temporel plutôt que le champ d'état déclassera donc une vulnérabilité activement exploitée par un acteur étatique. C'est un défaut de données, pas un défaut de sécurité, mais il se traduit directement en délai de correction.
Et la fenêtre. Cinq semaines séparent l'horodatage de compilation du 7 juillet du correctif du 11 août ; quatre jours seulement séparent le signalement au MSRC de l'assignation du CVE, et quatorze jours le signalement du correctif — ce qui, pour un défaut noyau exploité en 0-day, est rapide. Le problème n'est pas la réactivité de l'éditeur : elle est bonne. Le problème est que la phase où le défenseur avait encore de la visibilité s'était déjà refermée sur chaque machine atteinte, et qu'aucun correctif publié le 11 août ne restitue la télémétrie effacée le 7 juillet. Pour un parc en 24H2 ou 25H2, la question utile aujourd'hui n'est donc pas « avons-nous appliqué le cumulatif du 11 août » mais « disposons-nous, pour la période de juillet, d'événements de chargement d'image que le poste n'a pas pu réécrire ».
Une dernière lecture, celle des échéances. Les trois ajouts au KEV du 11 août n'ont pas reçu le même délai. CVE-2026-20349 sur Cisco ASA/FTD et la SQLi Metabase sont dues au 14 août, soit trois jours ; CVE-2026-68820 est due au 25 août, soit quatorze. CISA accorde donc quatre fois plus de temps à une élévation de privilèges noyau exploitée par un acteur étatique qu'à un déni de service sur un pare-feu. La logique de BOD 26-04 est cohérente et tient à l'exposition : l'ASA est en bordure et joignable depuis Internet sans authentification, AFD.sys exige un pied préalable sur la machine. Mais le calcul suppose que l'attaquant part de l'extérieur. Contre une chaîne qui commence par une offre d'emploi sur LinkedIn et un lecteur PDF signé, le pied préalable n'est pas un obstacle : c'est la phase 1, et elle était déjà franchie cinq semaines avant que l'échéance ne commence à courir.
