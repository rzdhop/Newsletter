Partie 02  ·  Deep-dive
Le cluster comme identité unique : extraire les secrets CNO/VCO de WSFC
Windows Server Failover Cluster réplique le mot de passe du Cluster Name Object sur chaque nœud. C’est fonctionnellement nécessaire, et c’est ce qui fait du cluster une cible unique.
Plan de la partie
1
 Ce qu’est un CNO, et pourquoi il est Tier Zero de fait.
2
 Où vit le secret : CLUSDB, checkpoints registre, structure _NNPWD_STRUCTURE.
3
 Le déchiffrement : NetNameLib::CryptoAccessV2::Decrypt dans clusres.dll.
4
 Le pivot RBCD : de Domain Computers à un ticket de service forgé.
5
 Pourquoi Impacket casse : il n’y a pas d’ADMIN$ sur un CNO.
6
 Limites, prérequis, et ce que la rotation horaire ne protège pas.
Garrett Foster a publié le 29 juillet une étude sur Windows Server Failover Cluster qui n’a pas de CVE et n’en aura pas. Ce n’est pas un bug : c’est une propriété de conception dont la conséquence offensive est rarement énoncée. Un cluster de basculement existe pour qu’un service survive à la perte d’un nœud. Pour cela, l’identité du service doit pouvoir être portée par n’importe quel nœud, à tout moment, sans intervention. Donc chaque nœud détient le secret de cette identité. La redondance qui protège de la panne matérielle supprime, par construction, l’isolation entre nœuds.
L’objet central est le Cluster Name Object (CNO), un compte machine Active Directory qui porte l’identité du cluster. À côté, un Virtual Computer Object (VCO) par point d’accès applicatif : une instance SQL en cluster, un rôle de partage de fichiers, un point d’accès ADFS. La base du cluster vit dans C:\Windows\Cluster\CLUSDB et est montée sous HKLM\Cluster. Le processus RHS.exe — Resource Host Subsystem — charge les DLL de ressources et porte les sessions de logon des identités de cluster. Les volumes partagés sont montés sous C:\ClusterStorage.
Foster résume la conséquence sans détour : compromettre un seul nœud vaut compromission complète du cluster. Ce qui compte pour un opérateur, c’est qu’un CNO ne ressemble pas à un compte à privilèges. C’est un compte machine ordinaire dans l’annuaire, sans marqueur particulier. Sa criticité vient de ce qu’il porte, pas de ce qu’il est — et c’est exactement pourquoi il échappe aux inventaires de comptes sensibles.
Où vit le secret. Le mot de passe du CNO n’est pas stocké là où l’on chercherait un secret de service. Il vit dans des checkpoints du registre, chiffré, avec les éléments de déchiffrement à côté. Trois emplacements comptent.
Emplacements registre — base de cluster
HKLM\CLUSTER\[GUID]\CryptoContainerGuid -> identifiant du conteneur cryptographique associe a la ressource HKLM\Cluster\Checkpoints\[GUID]\Crypto\Checkpoints -> materiel de cle, replique sur chaque noeud du cluster HKLM\Cluster\Resources\[GUID]\Parameters\ResourceData -> blob chiffre, format _NNPWD_STRUCTURE contient le mot de passe courant ET le precedent
Le blob et de quoi le lire sont voisins dans la même ruche, sur chaque nœud.
Le détail qui mérite qu’on s’y arrête est le stockage double. La structure _NNPWD_STRUCTURE contient le mot de passe courant et le précédent. La raison est fonctionnelle et parfaitement légitime : la rotation n’est pas atomique à travers les nœuds, il faut donc accepter l’ancien secret pendant la convergence. Les mots de passe de cluster tournent par défaut toutes les heures, ce qui ressemble à une bonne posture. Mais conserver le précédent signifie que la rotation ne ferme pas la fenêtre : elle la maintient ouverte sur deux générations. Un secret capturé juste avant une rotation reste valide après.
Le déchiffrement. Foster identifie NetNameLib::CryptoAccessV2::Decrypt dans clusres.dll comme la fonction qui traite le blob, en créditant le PoC de déchiffrement d’Evan McBroom. Le chemin d’exécution légitime, côté service de cluster, vaut d’être lu pour lui-même : c’est la carte de ce qu’on peut intercepter.
Chaîne d'obtention d'un jeton pour une identité de cluster
NetName::Identity::ObtainNewTokenOperation | +--> NNCommon::NNClusterCrypto::DecryptPassword | lit ResourceData, dechiffre via le conteneur crypto | +--> NetNameLib::CredentialAccess::Logon ouvre une session de logon pour le CNO / VCO le jeton reste vivant dans RHS.exe
RHS.exe conserve des jetons persistants pour CNO et VCO : deux surfaces, le blob au repos et le jeton en mémoire.
Il y a donc deux voies vers la même identité. La voie hors ligne lit le blob et le matériel de clé dans le registre, puis déchiffre. La voie en ligne cible les sessions de logon que RHS.exe maintient déjà. Les deux supposent un accès administrateur local sur un nœud ; aucune des deux n’est une élévation depuis rien.
⚠️ Hypothèse non testée
La voie par vol de jeton dans RHS.exe est une extrapolation de ma part. La publication documente que RHS.exe maintient des sessions persistantes pour CNO et VCO via ObtainNewTokenOperation, mais elle présente l’extraction par le registre — pas le vol de jeton — comme la technique réalisée. Traitez la voie en ligne comme plausible et non établie tant que personne ne l’a démontrée.
Le pivot RBCD. La partie réellement transposable ne part pas d’un nœud compromis. Elle part de l’annuaire. La délégation contrainte basée sur les ressources permet d’écrire l’attribut ms-DS-AllowedToActOnBehalfOfOtherIdentity sur un objet ordinateur que l’on contrôle, puis d’obtenir par S4U2Proxy un ticket de service pour n’importe quel utilisateur. Le prérequis est la permission WriteAccountRestrictions sur les nœuds du cluster, et l’appartenance à Domain Computers suffit à fournir l’objet ordinateur contrôlé.
Ce qui rend la manœuvre particulièrement rentable contre un cluster est énoncé ainsi par Foster : le nœud hébergeant le rôle CNO peut déchiffrer le ticket de service forgé, parce qu’il a accès au mot de passe du CNO stocké dans la base du cluster. Autrement dit, le partage de secret qui rend le basculement transparent rend aussi le ticket forgé acceptable partout. Un ticket qui, face à un service ordinaire, ne vaudrait que contre un hôte précis devient valide face à l’ensemble.
Pourquoi l’outillage habituel casse. C’est le passage le plus utile opérationnellement, et le moins prévisible. Un CNO ou un VCO n’expose que ClusterStorage$ et IPC$. Il n’y a pas d’ADMIN$. Or wmiexec.py et atexec.py d’Impacket écrivent la sortie de commande dans un fichier temporaire sur ADMIN$ avant de la relire. Sans ce partage, les outils échouent — non pas parce que l’authentification a échoué, mais parce que l’étape de récupération de sortie n’a nulle part où écrire. Un opérateur qui n’a pas ce modèle en tête conclura à tort que ses identifiants sont mauvais, et abandonnera un accès qui fonctionnait.
Le service de cluster maintient en outre un handle sur C:\ClusterStorage, ce qui bloque l’écriture arbitraire sur le seul partage restant — une tentative d’écriture directe sur ClusterStorage$ échoue en accès refusé pour cette raison, et non pour un problème de droits. Le contournement documenté consiste à renoncer à la sortie : le drapeau -silentcommand supprime la redirection, et la création de tâche par RPC permet l’exécution sans capture. On exécute à l’aveugle.
La boucle de migration. C’est ici que la technique devient réellement élégante, et c’est la partie qu’un résumé rapide manque. Une fois que l’on exécute dans le contexte du CNO, on n’exécute que sur un nœud : celui qui héberge le rôle à cet instant. Or le propre d’un cluster est que ce rôle se déplace. fustercluck automatise ce déplacement, et l’attaquant s’en sert comme d’un mécanisme de mouvement latéral fourni par la cible elle-même.
Boucle CNO — exécution sur chaque nœud à tour de rôle
# 1. ticket de service forge pour le CNO (via RBCD / S4U2Proxy) # 2. execution sur le noeud qui heberge actuellement le role atexec.py -silentcommand [payload] # 3. identifier le noeud porteur, puis migrer le role fustercluck.py enum_cluster fustercluck.py get_groupstate Cluster\ Group # 4. le role bascule -> rejouer atexec.py pour le noeud suivant atexec.py -silentcommand [payload] # 5. repeter jusqu'a avoir couvert tous les noeuds
Le basculement, concu pour la haute disponibilite, sert de primitive de mouvement lateral.
L’opération ne casse rien et ne déclenche aucune anomalie fonctionnelle : migrer un groupe de ressources est une opération d’administration normale, c’est même ce que l’on fait avant une maintenance. L’attaquant utilise la fonction de basculement pour sa finalité nominale, avec une intention différente. Il n’y a pas d’exploit dans cette étape — seulement l’usage documenté d’une API d’administration par quelqu’un qui a obtenu l’identité qui y donne droit.
Pourquoi le secret est partout : PaxosTag. La réplication de la base de cluster suit un protocole de consensus dont le marqueur est visible et lisible. Le PaxosTag a la forme NextEpochNumber:LastEpochNumber:SequenceNumber. À chaque changement de configuration, le SequenceNumber s’incrémente et une proposition part vers les autres nœuds ; ceux qui constatent un numéro local inférieur acceptent la proposition et répliquent la configuration.
Les mots de passe CNO et VCO voyagent dans ce flux. Foster le formule sans détour : ils sont répliqués à travers le cluster et présents sur chaque nœud, parce que si la ressource bascule vers un autre nœud, les clés doivent avoir basculé avec elle — via des checkpoints stockés en dehors de la base de cluster. Le secret n’est donc pas copié par négligence : il est copié par le mécanisme qui rend la disponibilité possible. Corollaire défensif utile, que Foster mentionne : l’itération du PaxosTag dans la base de cluster est un journal de changements de configuration, donc un endroit où une modification non autorisée laisse une trace.

Quatre chemins vers l'identité de cluster, et ce que chacun coûte réellement.
Limites et arbitrages. Premier point, et il est structurel : il n’y a pas de correctif à attendre. Le partage du secret entre nœuds est ce qui rend le basculement possible. Microsoft ne peut pas le supprimer sans supprimer la fonctionnalité. Ce qui se corrige, ce sont les conditions autour — la délégation, le classement en Tier Zero, la surveillance — pas le mécanisme.
Deuxième point : la voie registre n’est pas une élévation de privilèges. Elle suppose l’administration locale d’un nœud. Sa valeur est celle d’un multiplicateur. La technique elle-même ne franchit aucune frontière ; elle exploite le fait que la frontière n’a jamais existé entre les nœuds. Ce que le cluster porte détermine alors ce que la compromission vaut, et Foster détaille quatre débouchés concrets.
Un cluster ADFS adossé à un groupe de disponibilité SQL permet de forger des assertions SAML — donc de s’authentifier comme n’importe qui auprès de tout service fédéré. Une base SCCM en cluster donne le contrôle de SCCM et, par extension, de l’ensemble de ses clients. Un Exchange Database Availability Group est bâti sur WSFC : compromettre le cluster compromet toutes les boîtes aux lettres. AD CS, enfin, dispose d’une intégration WSFC documentée par Microsoft. La conclusion de Foster est sans nuance : dès que le cluster porte un service Tier Zero, chaque nœud, le CNO et chaque VCO doivent être traités comme des actifs Tier Zero.
Troisième point, une limite d’outillage que Foster signale lui-même : la corrélation d’un VCO vers son CNO exige l’analyse des DACL, et l’énumération des nœuds n’a pas de méthode fiable par le seul annuaire — il faut passer par des requêtes COM, IOXIDResolver et ServerAlive2 servant à énumérer les interfaces réseau. C’est la raison pour laquelle un collector dédié était nécessaire : WSFCHound étend BloodHound via OpenGraph, fustercluck couvre l’énumération et la migration de CNO, ludus_wsfc déploie le laboratoire.
La discrimination par SPN, en revanche, est propre et se fait en lecture seule. Les trois rôles se distinguent sans ambiguïté par leur classe de service.
Discrimination des rôles de cluster par classe de SPN
CNO MSServerCluster <- identifiant unique du cluster VCO MSClusterVirtualServer <- et PAS MSServerCluster Noeud membre MSServerClusterMgmtAPI <- et aucun des deux ci-dessus
Trois classes de SPN, trois roles : de quoi batir un inventaire sans rien ecrire dans l'annuaire.
L’ordre de grandeur justifie l’effort d’inventaire. Foster donne un chiffre issu du parc BloodHound Enterprise : 82 % des environnements observés comportaient au moins un cluster, pour une moyenne de 141 par environnement. Ce n’est pas une technologie de niche que l’on rencontrerait chez un client sur dix.
Quatrième point, et il déplace la responsabilité : la permission qui rend le pivot RBCD possible est parfois recommandée. Foster relève que certaines documentations Microsoft conseillent de déléguer WriteAccountRestrictions à des groupes larges, Domain Computers compris, alors que la recommandation sûre consiste à n’accorder au CNO que le droit de créer des objets ordinateur dans une OU précisément délimitée. La configuration exploitable n’est donc pas nécessairement une erreur d’administrateur ; elle peut être le résultat d’avoir suivi une consigne. C’est ce qui rend l’audit de cette ACL prioritaire sur l’audit d’une négligence supposée.
Cinquième point, et c’est là que le coût défensif est le plus intéressant. Le signal le plus propre est trivial à décrire et rarement collecté : les ressources CNO et VCO peuvent s’authentifier depuis tous les nœuds membres, mais le pool d’adresses sources doit rester statique. Un logon de CNO depuis une adresse hors du pool de nœuds est anormal par construction, sans faux positif structurel. Le corollaire opérationnel est direct : l’usage d’une identité de cluster depuis une machine qui n’est pas un nœud est détectable à coût nul par quiconque a pensé à l’écrire. La seconde détection recommandée — accès à la clé de registre ResourceData en dehors du service de cluster et de ses processus enfants — est plus coûteuse à instrumenter, mais elle frappe la voie hors ligne à la racine.
