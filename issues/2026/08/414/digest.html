KindaRails2Shell : un fichier MATLAB lit vos secrets sur Rails (CVE-2026-66066)
Pourquoi ça compte : Depuis Rails 7, le variant processor par défaut d'ActiveStorage est libvips, et libvips choisit son loader en reniflant les octets, pas l'extension ni le type MIME déclaré. Un fichier MATLAB v7.3 n'est pas un format : c'est un conteneur HDF5. Or HDF5 propose external storage (H5Pset_external) : la creation property list d'un dataset porte une liste de triplets (fichier, offset, taille), et la lecture ouvre ces fichiers de façon transparente. libmatio, utilisée par libvips pour lire les MAT v7.3, ne valide que le chunking ; elle n'appelle jamais H5Pget_external_count(), donc H5Dread ouvre le chemin déclaré et recopie ses octets dans la variable. libvips marque plusieurs de ces loaders comme untrusted ; ActiveStorage n'utilisait pas ce drapeau par défaut. Ethiack publie la chaîne complète maintenant que Rails a sorti son dépôt de détails techniques et d'outillage forensique, et que des PoC circulent.

COLDCARD : un #ifdef mal écrit ramène la génération de clés à 2^32
Pourquoi ça compte : Cas d'école de bug d'intégration, pas de cryptographie. La configuration de la carte définit MICROPY_HW_ENABLE_RNG à zéro, parce que COLDCARD fournit son propre wrapper de RNG matériel. libngu teste si la macro est définie au lieu de tester si elle est activée : la compilation réussit et ngu.random se lie au rng_get() de MicroPython, c'est-à-dire au générateur logiciel déterministe Yasmarang initialisé depuis l'UID du MCU et des registres de timer. Partie 02  ·  Deep-dive
Le timer qui survit à son device : UAF dans le bridge STP de Linux
Deux chemins de destruction, un seul annule les timers. SSD Secure Disclosure, TyphoonPWN 2026.
SSD Secure Disclosure a publié ce matin, 5 août à 08:33 UTC, l'analyse d'un use-after-free dans l'implémentation Spanning Tree Protocol du bridge logiciel de Linux. Le bug a été soumis par deux chercheurs indépendants, n132 et sven sze, et a pris la deuxième place de la catégorie Linux PE au TyphoonPWN 2026. L'avis référence le commit correctif 2a00517db8de4be7df3d483b215c5544fb30a191 dans l'arbre de Torvalds. Le texte de l'analyse fait 530 mots ; le reste de la publication est le code de l'exploit. C'est peu, et c'est pourtant l'un des bugs les plus proprement expliqués de la semaine, parce que la faute tient entièrement dans une asymétrie entre deux fonctions.
L'intérêt pour un opérateur n'est pas la cible — peu de gens attaquent un bridge Linux depuis l'extérieur. C'est que toute la chaîne se pilote depuis un espace de noms réseau non privilégié via netlink : créer un bridge, activer STP, forcer l'état d'un port, supprimer le lien. Aucune de ces opérations ne ressemble à une attaque prise isolément.
Le chemin exploité
1
 Créer un bridge et le laisser administrativement DOWN. C'est la condition non intuitive : tout le monde teste le chemin UP.
2
 Activer STP côté noyau (BR_KERNEL_STP), via l'attribut netlink IFLA_BR_STP_STATE.
3
 Rattacher un port et le pousser dans l'état LEARNING. Le chemin d'armement ne vérifie jamais IFF_UP : les timers partent alors que le bridge est éteint.
4
 Supprimer le lien avec RTM_DELLINK. Le net_device est libéré, mais les timers restent chaînés sur une timer base per-CPU.
5
 Attendre quelques secondes. __run_timers() fait feu sur un timer_list qui pointe dans un slab libéré.
La durée de vie des timers STP est celle du net_device, et pas parce que quelqu'un l'a décidé : c'est structurel. Les timers sont des champs de struct net_bridge, et struct net_bridge vit dans la zone de données privées du net_device du bridge. On retrouve dans net/bridge/br_private.h hello_timer, tcn_timer et topology_change_timer côté bridge, plus forward_delay_timer, hold_timer et message_age_timer par port. Libérer le device sans avoir supprimé ces timers est donc, mécaniquement, un use-after-free. Toute la question est de savoir quel chemin de destruction fait le ménage.
Un seul le fait. br_stp_disable_bridge() est la seule fonction qui supprime les timers de façon synchrone, et elle n'est atteinte que depuis br_dev_stop(), c'est-à-dire depuis ndo_stop, c'est-à-dire lors d'une transition UP vers DOWN :
net/bridge/br_stp_if.c
void br_stp_disable_bridge(struct net_bridge *br) { struct net_bridge_port *p; spin_lock_bh(&br->lock); list_for_each_entry(p, &br->port_list, list) { if (p->state != BR_STATE_DISABLED) br_stp_disable_port(p); } __br_set_topology_change(br, 0); br->topology_change_detected = 0; spin_unlock_bh(&br->lock); timer_delete_sync(&br->hello_timer); timer_delete_sync(&br->topology_change_timer); timer_delete_sync(&br->tcn_timer); cancel_delayed_work_sync(&br->gc_work); }
Les quatre annulations synchrones qui rendent la destruction sûre. Elles ne sont exécutées que sur le chemin ndo_stop.
L'autre chemin ne passe pas par là. Supprimer directement le lien conduit à br_dev_delete(), qui n'appelle jamais br_stp_disable_bridge(). Et unregister_netdevice_many() saute purement et simplement ndo_stop pour un device déjà DOWN — ce qui est logique : à quoi bon arrêter ce qui est déjà arrêté. L'hypothèse implicite est qu'un device DOWN n'a rien d'armé. C'est cette hypothèse qui ne tient pas.
Elle ne tient pas parce que le chemin d'armement ne regarde pas l'état administratif du bridge. br_stp_enable_bridge() est prudent : il ne réactive un port que si netif_running(p->dev) et netif_oper_up(p->dev). Mais ce test porte sur le device du port, pas sur celui du bridge. Plus bas, dans br_make_forwarding(), l'armement est inconditionnel :
net/bridge/br_stp.c
static void br_make_forwarding(struct net_bridge_port *p) { struct net_bridge *br = p->br; if (p->state != BR_STATE_BLOCKING) return; if (br->stp_enabled == BR_NO_STP || br->forward_delay == 0) { br_set_state(p, BR_STATE_FORWARDING); br_topology_change_detection(br); timer_delete(&p->forward_delay_timer); } else if (br->stp_enabled == BR_KERNEL_STP) br_set_state(p, BR_STATE_LISTENING); else br_set_state(p, BR_STATE_LEARNING); br_ifinfo_notify(RTM_NEWLINK, NULL, p); if (br->forward_delay != 0) mod_timer(&p->forward_delay_timer, jiffies + br->forward_delay); }
Le mod_timer final ne dépend que de forward_delay. Ni IFF_UP ni netif_running n'apparaissent dans cette fonction.
La fonction qui appelle br_make_forwarding() vaut aussi le coup d'œil, parce qu'elle montre que le sous-système entier raisonne sur l'état STP des ports et jamais sur l'état administratif du bridge. br_port_state_selection() ignore les ports DISABLED, s'abstient si l'espace utilisateur pilote STP (BR_USER_STP), puis répartit les autres entre forwarding et blocking selon qu'ils sont root port ou designated port. Et elle se termine par ceci :
net/bridge/br_stp.c — fin de br_port_state_selection()
if (p->state == BR_STATE_FORWARDING) ++liveports; } if (liveports == 0) netif_carrier_off(br->dev); else netif_carrier_on(br->dev); }
Un bridge administrativement DOWN se voit ici manipuler son carrier. Le code ne se demande jamais s'il a le droit d'agir sur ce device.
Chemin Déclencheur Passe par ndo_stop Timers annulés
ndo_stop transition UP vers DOWN (ip link set down) oui, par définition oui — br_dev_stop() appelle br_stp_disable_bridge()
dellink, device UP RTM_DELLINK sur un bridge actif oui, arrêt implicite avant unregister oui, par le même chemin
dellink, device DOWN RTM_DELLINK sur un bridge jamais monté non — unregister_netdevice_many() le saute non — br_dev_delete() ne touche pas au STP
Trois façons de détruire un bridge, une seule laisse des timers armés. La troisième ligne est le bug.
Reste la primitive. Un timer_list expiré est traité par __run_timers() en contexte softirq, qui finit dans call_timer_fn() : le champ function est appelé avec, en premier argument, l'adresse du timer_list lui-même. Autrement dit, si l'on parvient à réoccuper le slot libéré avec un contenu maîtrisé, on obtient à la fois le pointeur de code et le contenu pointé par RDI. L'avis situe l'objet libéré dans le cache kmalloc-cg-8k, et souligne la propriété qui rend l'ensemble praticable : les timers vont s'exécuter tout seuls quelques secondes plus tard. Il n'y a pas de primitive de déclenchement à trouver, pas d'appel système à rejouer pour atteindre l'objet mort. Le noyau le fait à la place de l'attaquant.
Le code publié avec l'avis mérite qu'on s'y arrête, parce qu'il documente le pilotage. La mise en état d'un port ne passe pas par la machine à états STP : bridgePortStateSet() envoie un RTM_SETLINK avec ifi_family à AF_BRIDGE et un attribut IFLA_PROTINFO non imbriqué, ce que le commentaire du code décrit comme frappant br_set_port_state() directement. C'est ce qui permet de placer un port en BR_STATE_LEARNING (valeur 2) sans négocier quoi que ce soit avec un vrai réseau STP.
exploit publié par SSD — bridge.c
char * bridgePortStateSet(const char *iface, __u8 state) { struct newlink_req *req = calloc(1, sizeof(struct newlink_req)); req->nlh.nlmsg_type = RTM_SETLINK; req->nlh.nlmsg_flags = NLM_F_REQUEST | NLM_F_ACK; req->nlh.nlmsg_len = NLMSG_LENGTH(sizeof(struct ifinfomsg)); req->ifi.ifi_family = AF_BRIDGE; req->ifi.ifi_index = if_nametoindex(iface); /* IFLA_PROTINFO (not nested) - hits br_set_port_state() directly */ req->nlh.nlmsg_len += NLMSG_ALIGN(add_rtattr( (size_t)req + NLMSG_ALIGN(req->nlh.nlmsg_len), IFLA_PROTINFO, sizeof(__u8), (char *)&state)); return (char *)req; }
BR_STATE_LEARNING vaut 2. Le reste de la bibliothèque publiée est du netlink de confort : bridgeAdd, bridgeStpSet, linkDel.
Mises bout à bout, les primitives publiées donnent la séquence de mise en condition. Elle tient en cinq messages netlink, dont aucun n'est privilégié dans un espace de noms réseau où l'appelant détient CAP_NET_ADMIN :
séquence reconstituée depuis les helpers publiés par SSD
bridgeAdd("br0") /* RTM_NEWLINK, kind = "bridge" */ bridgeStpSet("br0", 1) /* IFLA_BR_STP_STATE = BR_KERNEL_STP */ bridgePortAdd("br0", "dummy0") /* IFLA_MASTER */ bridgePortStateSet("dummy0", 2) /* BR_STATE_LEARNING */ /* br0 n'a jamais ete monte : pas de IFF_UP, donc pas de ndo_stop */ linkDel("br0") /* RTM_DELLINK -> free_netdev() */
Aucun de ces cinq appels ne ressemble a une attaque pris isolement. C'est l'ordre, et l'absence du IFF_UP, qui font le bug.
⚠️ Hypothèse non testée
L'avis ne dit pas avec quel objet le slot de 8 Ko est réoccupé. La bibliothèque publiée contient loopbackSend2(priority, len), qui ouvre un socket UDP sur la loopback, positionne SO_PRIORITY, puis écrit une longueur choisie corrigée de 0x2a octets d'en-têtes — la forme canonique d'un spray par sk_buff avec contrôle simultané de la taille et du bucket. Que ce soit là la primitive de refill est une lecture de ma part, cohérente avec le suffixe -cg du cache (allocations comptabilisées par cgroup) mais que le texte de SSD n'établit pas. Je n'ai pas reproduit l'exploit.
Le reste de la bibliothèque publiée dit quelque chose sur la manière dont le bug a été trouvé. On y trouve une fonction syz_net_reset() qui descend l'interface lo, supprime sa qdisc racine par un RTM_DELQDISC avec tcm_parent à 0xFFFFFFFF, puis la remonte — l'idiome de remise à zéro d'état de syzkaller, sous son nom d'origine. La forme du bug va dans le même sens : une combinaison d'états que personne ne compose à la main (bridge jamais monté, STP noyau actif, port en LEARNING, suppression du lien) mais qu'un fuzzer netlink atteint mécaniquement. Ce qui reste au crédit des chercheurs, et que le fuzzer ne donne pas, c'est la remontée du crash jusqu'à l'asymétrie entre les deux chemins de destruction, puis jusqu'à une primitive de détournement de flot.
Limites et compromis, maintenant. La première est la fenêtre temporelle : entre le free et le tir du timer il y a quelques secondes, ce qui est confortable pour pulvériser le tas mais laisse aussi le noyau réutiliser le slot pour n'importe quoi d'autre. Un échec ne donne pas un second essai propre : il donne un appel indirect vers une adresse arbitraire en contexte softirq, c'est-à-dire une panique. La deuxième est le cache visé. kmalloc-cg-8k est un bucket peu fréquenté comparé aux caches génériques, ce qui aide au déterminisme, mais impose que l'objet de remplissage soit lui aussi comptabilisé cgroup — cela exclut une partie du catalogue habituel de spray.
La troisième limite est celle qui décide de la portée réelle. Toute la séquence est du netlink sur un bridge que l'attaquant crée lui-même : si l'environnement autorise les user namespaces non privilégiés avec CAP_NET_ADMIN dans le namespace, c'est une élévation locale depuis un compte quelconque, ce qui est le cadre d'un TyphoonPWN Linux PE. Si la distribution restreint unprivileged_userns_clone, ou si l'on est déjà dans un conteneur sans NET_ADMIN, la primitive n'est pas atteignable du tout. C'est la différence habituelle entre un bug de sous-système réseau et un bug exploitable : la surface est configurable, et elle est souvent déjà fermée sur un serveur durci.
Dernier point, éditorial. La forme de ce bug — deux chemins de destruction dont un seul fait le ménage, parce qu'un test d'état a été placé sur le chemin nominal et pas sur l'autre — est exactement celle de la fenêtre TOCTOU de PsSetLoadImageNotifyRoutine traitée dans le numéro 412. Ce ne sont pas les mêmes systèmes d'exploitation ni la même classe de bug, mais c'est la même faute de raisonnement : un invariant vérifié à un endroit, supposé partout ailleurs.
