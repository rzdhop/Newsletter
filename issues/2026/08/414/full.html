KindaRails2Shell : un fichier MATLAB lit vos secrets sur Rails (CVE-2026-66066)
Pourquoi ça compte : Depuis Rails 7, le variant processor par défaut d'ActiveStorage est libvips, et libvips choisit son loader en reniflant les octets, pas l'extension ni le type MIME déclaré. Un fichier MATLAB v7.3 n'est pas un format : c'est un conteneur HDF5. Or HDF5 propose external storage (H5Pset_external) : la creation property list d'un dataset porte une liste de triplets (fichier, offset, taille), et la lecture ouvre ces fichiers de façon transparente. libmatio, utilisée par libvips pour lire les MAT v7.3, ne valide que le chunking ; elle n'appelle jamais H5Pget_external_count(), donc H5Dread ouvre le chemin déclaré et recopie ses octets dans la variable. libvips marque plusieurs de ces loaders comme untrusted ; ActiveStorage n'utilisait pas ce drapeau par défaut. Partie 02  ·  Deep-dive
Le timer qui survit à son device : UAF dans le bridge STP de Linux
Deux chemins de destruction, un seul annule les timers. SSD Secure Disclosure, TyphoonPWN 2026.
SSD Secure Disclosure a publié ce matin, 5 août à 08:33 UTC, l'analyse d'un use-after-free dans l'implémentation Spanning Tree Protocol du bridge logiciel de Linux. Le bug a été soumis par deux chercheurs indépendants, n132 et sven sze, et a pris la deuxième place de la catégorie Linux PE au TyphoonPWN 2026. L'avis référence le commit correctif 2a00517db8de4be7df3d483b215c5544fb30a191 dans l'arbre de Torvalds. Le texte de l'analyse fait 530 mots ; le reste de la publication est le code de l'exploit. C'est peu, et c'est pourtant l'un des bugs les plus proprement expliqués de la semaine, parce que la faute tient entièrement dans une asymétrie entre deux fonctions.
L'intérêt pour un opérateur n'est pas la cible — peu de gens attaquent un bridge Linux depuis l'extérieur. C'est que toute la chaîne se pilote depuis un espace de noms réseau non privilégié via netlink : créer un bridge, activer STP, forcer l'état d'un port, supprimer le lien. Aucune de ces opérations ne ressemble à une attaque prise isolément.
Le chemin exploité
1
 Créer un bridge et le laisser administrativement DOWN. C'est la condition non intuitive : tout le monde teste le chemin UP.
2
 Activer STP côté noyau (BR_KERNEL_STP), via l'attribut netlink IFLA_BR_STP_STATE.
3
 Rattacher un port et le pousser dans l'état LEARNING. Le chemin d'armement ne vérifie jamais IFF_UP : les timers partent alors que le bridge est éteint.
4
 Supprimer le lien avec RTM_DELLINK. Le net_device est libéré, mais les timers restent chaînés sur une timer base per-CPU.
5
 Attendre quelques secondes. __run_timers() fait feu sur un timer_list qui pointe dans un slab libéré.
La durée de vie des timers STP est celle du net_device, et pas parce que quelqu'un l'a décidé : c'est structurel. Les timers sont des champs de struct net_bridge, et struct net_bridge vit dans la zone de données privées du net_device du bridge. On retrouve dans net/bridge/br_private.h hello_timer, tcn_timer et topology_change_timer côté bridge, plus forward_delay_timer, hold_timer et message_age_timer par port. Libérer le device sans avoir supprimé ces timers est donc, mécaniquement, un use-after-free. Toute la question est de savoir quel chemin de destruction fait le ménage.
Un seul le fait. br_stp_disable_bridge() est la seule fonction qui supprime les timers de façon synchrone, et elle n'est atteinte que depuis br_dev_stop(), c'est-à-dire depuis ndo_stop, c'est-à-dire lors d'une transition UP vers DOWN :
net/bridge/br_stp_if.c
void br_stp_disable_bridge(struct net_bridge *br) { struct net_bridge_port *p; spin_lock_bh(&br->lock); list_for_each_entry(p, &br->port_list, list) { if (p->state != BR_STATE_DISABLED) br_stp_disable_port(p); } __br_set_topology_change(br, 0); br->topology_change_detected = 0; spin_unlock_bh(&br->lock); timer_delete_sync(&br->hello_timer); timer_delete_sync(&br->topology_change_timer); timer_delete_sync(&br->tcn_timer); cancel_delayed_work_sync(&br->gc_work); }
Les quatre annulations synchrones qui rendent la destruction sûre. Elles ne sont exécutées que sur le chemin ndo_stop.
L'autre chemin ne passe pas par là. Supprimer directement le lien conduit à br_dev_delete(), qui n'appelle jamais br_stp_disable_bridge(). Et unregister_netdevice_many() saute purement et simplement ndo_stop pour un device déjà DOWN — ce qui est logique : à quoi bon arrêter ce qui est déjà arrêté. L'hypothèse implicite est qu'un device DOWN n'a rien d'armé. C'est cette hypothèse qui ne tient pas.
Elle ne tient pas parce que le chemin d'armement ne regarde pas l'état administratif du bridge. br_stp_enable_bridge() est prudent : il ne réactive un port que si netif_running(p->dev) et netif_oper_up(p->dev). Mais ce test porte sur le device du port, pas sur celui du bridge. Plus bas, dans br_make_forwarding(), l'armement est inconditionnel :
net/bridge/br_stp.c
static void br_make_forwarding(struct net_bridge_port *p) { struct net_bridge *br = p->br; if (p->state != BR_STATE_BLOCKING) return; if (br->stp_enabled == BR_NO_STP || br->forward_delay == 0) { br_set_state(p, BR_STATE_FORWARDING); br_topology_change_detection(br); timer_delete(&p->forward_delay_timer); } else if (br->stp_enabled == BR_KERNEL_STP) br_set_state(p, BR_STATE_LISTENING); else br_set_state(p, BR_STATE_LEARNING); br_ifinfo_notify(RTM_NEWLINK, NULL, p); if (br->forward_delay != 0) mod_timer(&p->forward_delay_timer, jiffies + br->forward_delay); }
Le mod_timer final ne dépend que de forward_delay. Ni IFF_UP ni netif_running n'apparaissent dans cette fonction.
La fonction qui appelle br_make_forwarding() vaut aussi le coup d'œil, parce qu'elle montre que le sous-système entier raisonne sur l'état STP des ports et jamais sur l'état administratif du bridge. br_port_state_selection() ignore les ports DISABLED, s'abstient si l'espace utilisateur pilote STP (BR_USER_STP), puis répartit les autres entre forwarding et blocking selon qu'ils sont root port ou designated port. Et elle se termine par ceci :
net/bridge/br_stp.c — fin de br_port_state_selection()
if (p->state == BR_STATE_FORWARDING) ++liveports; } if (liveports == 0) netif_carrier_off(br->dev); else netif_carrier_on(br->dev); }
Un bridge administrativement DOWN se voit ici manipuler son carrier. Le code ne se demande jamais s'il a le droit d'agir sur ce device.
Chemin Déclencheur Passe par ndo_stop Timers annulés
ndo_stop transition UP vers DOWN (ip link set down) oui, par définition oui — br_dev_stop() appelle br_stp_disable_bridge()
dellink, device UP RTM_DELLINK sur un bridge actif oui, arrêt implicite avant unregister oui, par le même chemin
dellink, device DOWN RTM_DELLINK sur un bridge jamais monté non — unregister_netdevice_many() le saute non — br_dev_delete() ne touche pas au STP
Trois façons de détruire un bridge, une seule laisse des timers armés. La troisième ligne est le bug.
Reste la primitive. Un timer_list expiré est traité par __run_timers() en contexte softirq, qui finit dans call_timer_fn() : le champ function est appelé avec, en premier argument, l'adresse du timer_list lui-même. Autrement dit, si l'on parvient à réoccuper le slot libéré avec un contenu maîtrisé, on obtient à la fois le pointeur de code et le contenu pointé par RDI. L'avis situe l'objet libéré dans le cache kmalloc-cg-8k, et souligne la propriété qui rend l'ensemble praticable : les timers vont s'exécuter tout seuls quelques secondes plus tard. Il n'y a pas de primitive de déclenchement à trouver, pas d'appel système à rejouer pour atteindre l'objet mort. Le noyau le fait à la place de l'attaquant.
Le code publié avec l'avis mérite qu'on s'y arrête, parce qu'il documente le pilotage. La mise en état d'un port ne passe pas par la machine à états STP : bridgePortStateSet() envoie un RTM_SETLINK avec ifi_family à AF_BRIDGE et un attribut IFLA_PROTINFO non imbriqué, ce que le commentaire du code décrit comme frappant br_set_port_state() directement. C'est ce qui permet de placer un port en BR_STATE_LEARNING (valeur 2) sans négocier quoi que ce soit avec un vrai réseau STP.
exploit publié par SSD — bridge.c
char * bridgePortStateSet(const char *iface, __u8 state) { struct newlink_req *req = calloc(1, sizeof(struct newlink_req)); req->nlh.nlmsg_type = RTM_SETLINK; req->nlh.nlmsg_flags = NLM_F_REQUEST | NLM_F_ACK; req->nlh.nlmsg_len = NLMSG_LENGTH(sizeof(struct ifinfomsg)); req->ifi.ifi_family = AF_BRIDGE; req->ifi.ifi_index = if_nametoindex(iface); /* IFLA_PROTINFO (not nested) - hits br_set_port_state() directly */ req->nlh.nlmsg_len += NLMSG_ALIGN(add_rtattr( (size_t)req + NLMSG_ALIGN(req->nlh.nlmsg_len), IFLA_PROTINFO, sizeof(__u8), (char *)&state)); return (char *)req; }
BR_STATE_LEARNING vaut 2. Le reste de la bibliothèque publiée est du netlink de confort : bridgeAdd, bridgeStpSet, linkDel.
Mises bout à bout, les primitives publiées donnent la séquence de mise en condition. Elle tient en cinq messages netlink, dont aucun n'est privilégié dans un espace de noms réseau où l'appelant détient CAP_NET_ADMIN :
séquence reconstituée depuis les helpers publiés par SSD
bridgeAdd("br0") /* RTM_NEWLINK, kind = "bridge" */ bridgeStpSet("br0", 1) /* IFLA_BR_STP_STATE = BR_KERNEL_STP */ bridgePortAdd("br0", "dummy0") /* IFLA_MASTER */ bridgePortStateSet("dummy0", 2) /* BR_STATE_LEARNING */ /* br0 n'a jamais ete monte : pas de IFF_UP, donc pas de ndo_stop */ linkDel("br0") /* RTM_DELLINK -> free_netdev() */
Aucun de ces cinq appels ne ressemble a une attaque pris isolement. C'est l'ordre, et l'absence du IFF_UP, qui font le bug.
⚠️ Hypothèse non testée
L'avis ne dit pas avec quel objet le slot de 8 Ko est réoccupé. La bibliothèque publiée contient loopbackSend2(priority, len), qui ouvre un socket UDP sur la loopback, positionne SO_PRIORITY, puis écrit une longueur choisie corrigée de 0x2a octets d'en-têtes — la forme canonique d'un spray par sk_buff avec contrôle simultané de la taille et du bucket. Que ce soit là la primitive de refill est une lecture de ma part, cohérente avec le suffixe -cg du cache (allocations comptabilisées par cgroup) mais que le texte de SSD n'établit pas. Je n'ai pas reproduit l'exploit.
Le reste de la bibliothèque publiée dit quelque chose sur la manière dont le bug a été trouvé. On y trouve une fonction syz_net_reset() qui descend l'interface lo, supprime sa qdisc racine par un RTM_DELQDISC avec tcm_parent à 0xFFFFFFFF, puis la remonte — l'idiome de remise à zéro d'état de syzkaller, sous son nom d'origine. La forme du bug va dans le même sens : une combinaison d'états que personne ne compose à la main (bridge jamais monté, STP noyau actif, port en LEARNING, suppression du lien) mais qu'un fuzzer netlink atteint mécaniquement. Ce qui reste au crédit des chercheurs, et que le fuzzer ne donne pas, c'est la remontée du crash jusqu'à l'asymétrie entre les deux chemins de destruction, puis jusqu'à une primitive de détournement de flot.
Limites et compromis, maintenant. La première est la fenêtre temporelle : entre le free et le tir du timer il y a quelques secondes, ce qui est confortable pour pulvériser le tas mais laisse aussi le noyau réutiliser le slot pour n'importe quoi d'autre. Un échec ne donne pas un second essai propre : il donne un appel indirect vers une adresse arbitraire en contexte softirq, c'est-à-dire une panique. La deuxième est le cache visé. kmalloc-cg-8k est un bucket peu fréquenté comparé aux caches génériques, ce qui aide au déterminisme, mais impose que l'objet de remplissage soit lui aussi comptabilisé cgroup — cela exclut une partie du catalogue habituel de spray.
La troisième limite est celle qui décide de la portée réelle. Toute la séquence est du netlink sur un bridge que l'attaquant crée lui-même : si l'environnement autorise les user namespaces non privilégiés avec CAP_NET_ADMIN dans le namespace, c'est une élévation locale depuis un compte quelconque, ce qui est le cadre d'un TyphoonPWN Linux PE. Si la distribution restreint unprivileged_userns_clone, ou si l'on est déjà dans un conteneur sans NET_ADMIN, la primitive n'est pas atteignable du tout. C'est la différence habituelle entre un bug de sous-système réseau et un bug exploitable : la surface est configurable, et elle est souvent déjà fermée sur un serveur durci.
Dernier point, éditorial. La forme de ce bug — deux chemins de destruction dont un seul fait le ménage, parce qu'un test d'état a été placé sur le chemin nominal et pas sur l'autre — est exactement celle de la fenêtre TOCTOU de PsSetLoadImageNotifyRoutine traitée dans le numéro 412. Ce ne sont pas les mêmes systèmes d'exploitation ni la même classe de bug, mais c'est la même faute de raisonnement : un invariant vérifié à un endroit, supposé partout ailleurs.

Deux bugs, un désaccord de framing : request smuggling dans Hiawatha (CVE-2026-51785)
Un serveur qui se présente comme sécurisé, deux rôles opposés, et un mainteneur qui a refusé le bug avant de le corriger en silence.
Hiawatha est un serveur web développé depuis 2002 par une seule personne, sous GPLv2, qui met la sécurité en tête de ses objectifs affichés. Il fait à la fois serveur et reverse proxy, avec un cache et des ACL par IP ou par chemin. Fenrisk compte environ 6 100 services exposés sur Internet dont la bannière contient Server: Hiawatha, en précisant qu'il s'agit d'un plancher : les instances configurées avec un ServerString personnalisé ou vide ne sont pas comptées. Le chiffre n'est pas impressionnant, et là n'est pas l'intérêt : ce qui rend le cas instructif, c'est qu'un même produit fournit ici les deux moitiés d'une désynchronisation, et que l'article distingue proprement ce qui a été reproduit de ce qui ne l'a pas été.
Rappel de la règle qui est violée. Le RFC 9112 §6.3 dit que si un message arrive avec à la fois un Transfer-Encoding et un Content-Length, le Transfer-Encoding l'emporte, que la situation peut signaler une tentative de smuggling et doit être traitée comme une erreur, et qu'un intermédiaire qui choisit de transmettre le message DOIT d'abord retirer le Content-Length reçu avant de le relayer. Hiawatha 12.1 se trompe sur les deux points, dans deux fichiers différents.
Les deux défauts
1
 src/http.c — la logique de parsing teste Content-Length en premier et ne retombe sur le décodage chunked que si Content-Length est absent. Toute requête portant les deux en-têtes est donc découpée sur Content-Length : l'inverse exact de ce que demande le RFC.
2
 src/rproxy.c — dans send_request_to_webserver(), aucun chemin ne retire le Content-Length entrant quand un Transfer-Encoding est également présent. La requête ambiguë part telle quelle vers le back-end.
3
 Le premier défaut rend Hiawatha exploitable en tant que back-end (scénario TE.CL). Le second le rend exploitable en tant que front-end (scénario CL.TE).
4
 Le correctif 12.2 ne touche que http.c : il rejette en 400 toute requête portant les deux en-têtes. rproxy.c reste inchangé — le second défaut est neutralisé indirectement, parce qu'une requête ambiguë n'atteint plus jamais le chemin de relais.
src/http.c — avant (12.1) puis après (12.2)
/* 12.1 : le premier test gagne, l'ambiguite n'est jamais detectee */ if ((strstart = find_http_header(session->request, hs_conlen)) != NULL) { /* Request has Content-Length */ ... } else if (find_http_header(session->request, hs_chunked) != NULL) { /* Chunked transfer encoding */ ... } /* 12.2 : un seul if imbrique, et la requete ambigue meurt en 400 */ if ((strstart = find_http_header(session->request, hs_conlen)) != NULL) { /* Both content length and chunked transfer encoding not allowed */ if (find_http_header(session->request, hs_chunked) != NULL) { result = 400; break; } ... }
Quatre lignes ajoutées. Le correctif est minimal parce que la faute l'était aussi : un else-if là où il fallait un test d'exclusion.
Le premier scénario, Hiawatha en back-end, est celui qui demande le plus de chance. Il faut un reverse proxy en amont qui accepte la requête ambiguë sans erreur et qui relaie les deux en-têtes sans toucher au Content-Length — c'est-à-dire un proxy lui-même non conforme. Le proxy découpe alors le corps sur Transfer-Encoding et consomme tout ; Hiawatha, lui, découpe sur Content-Length, ne retient que les quatre premiers octets, et considère le reste comme le début de la requête suivante :
TE.CL — Hiawatha en back-end
POST / HTTP/1.1 Host: something.com Content-Length: 4 Transfer-Encoding: chunked 42 GET /smuggling HTTP/1.1 Host: something.com Content-Length: 42 0
Le second scénario est le vrai problème, et l'article a raison d'insister sur l'asymétrie des conditions. Hiawatha en front-end n'a besoin, en face, que d'un back-end conforme : un serveur qui fait ce que le RFC demande, c'est-à-dire découper sur Transfer-Encoding quand les deux en-têtes sont présents. Hiawatha fournit lui-même les deux moitiés du comportement non conforme — il découpe sur Content-Length (défaut 1) et relaie le tout sans nettoyer (défaut 2). La seule façon d'échapper à la désynchronisation est d'avoir en aval un serveur qui rejette carrément la requête ambiguë en 400.
CL.TE — Hiawatha en front-end
POST / HTTP/1.1 Host: something.com Transfer-Encoding: chunked Content-Length: 40 0 GET /smuggling HTTP/1.1 X-Ignore:
Le back-end traite le corps comme vide (chunk terminal 0) ; tout ce qui suit préfixe la requête suivante sur la connexion.
La démonstration retenue par Fenrisk est Hiawatha devant Caddy 2.11.4, avec une directive ReverseProxy en keep-alive. Deux impacts sont reproduits en laboratoire. Le premier est un contournement d'ACL : l'UrlToolkit de Hiawatha peut interdire /admin.html par un Match ... DenyAccess, et le tunneling de requête atteint la ressource malgré la règle. Le second est plus intéressant, parce qu'il utilise une seconde fonctionnalité du même produit contre lui-même.
hiawatha.conf — la configuration du laboratoire
# Hiawatha en front-end, Caddy 2.11.4 en back-end ReverseProxy .* http://caddy:80/ 10 keep-alive # la regle d'ACL que le smuggling contourne UrlToolkit { ToolkitID = block_admin Match ^/admin\.html$ DenyAccess } UseToolkit = block_admin # le cache qui transforme le contournement en effet persistant CacheSize = 32 CacheMaxFilesize = 1024 CacheRProxyExtensions = html, css, js, txt
Trois fonctionnalites de confort du produit. Chacune elargit l'impact du meme desaccord de framing.
Hiawatha embarque un cache (CacheSize, CacheMaxFilesize, CacheRProxyExtensions). En empoisonnant ce cache, la réponse de /admin.html est stockée sous la clé /index.html, et tout client demandant ensuite /index.html reçoit la page restreinte — alors qu'une requête directe sur /admin.html continue de répondre 403. Le détail opérationnel vaut d'être noté : la requête enveloppante ne doit pas se résoudre en /index.html sur Hiawatha, sinon Hiawatha met en cache la vraie page et l'empoisonnement échoue. Un cache buster sur la requête externe (une query string suffit) règle le problème pendant que la requête smugglée empoisonne bien l'entrée visée.
empoisonnement du cache — deux requêtes sur la même connexion
# 1. la requete enveloppante porte un cache buster (?x=a) pour que Hiawatha # ne mette PAS /index.html en cache avec sa vraie reponse GET /index.html?x=a HTTP/1.1 Host: something.com Content-Length: 41 Transfer-Encoding: chunked Content-Type: application/x-www-form-urlencoded 0 GET /admin.html HTTP/1.1 X-Ignore: # 2. la requete suivante est prefixee par le GET /admin.html smuggle ; # la reponse est stockee sous la cle /index.html GET /index.html HTTP/1.1 Host: something.com
Sans le cache buster, Hiawatha met en cache la vraie page et l'empoisonnement echoue. Le detail est dans l'article, il n'est pas evident.
Rôle de Hiawatha Condition en face Impact reproduit Impact conditionnel
Front-end (CL.TE) back-end conforme au RFC 9112 §6.3 — condition faible contournement d'ACL, empoisonnement de cache, DoS par ré-empoisonnement -
Back-end (TE.CL) proxy amont non conforme qui relaie les deux en-têtes — condition forte - divulgation du trafic d'autres utilisateurs si le proxy amont mutualise ses connexions
La ligne du haut est celle qui a été reproduite en laboratoire. Celle du bas porte le pire impact et n'a pas été démontrée.
⚠️ Hypothèse non testée
Le scénario back-end — capture de la requête d'une victime, cookies et identifiants compris — n'a pas été reproduit par Fenrisk, qui l'écrit noir sur blanc et le fait dépendre du comportement de réutilisation de connexions du proxy amont. Le score CVSS 3.1 publié, 9.6 critique en AV:N/AC:H/PR:N/UI:N/S:C/C:H/I:H/A:H, reflète ce déploiement-là, le pire. Dans la configuration effectivement montée en laboratoire, les auteurs annoncent eux-mêmes un vecteur plus bas, de l'ordre de C:L/I:H/A:L. Un 9.6 lu sans le paragraphe qui l'accompagne surestime donc ce qui a été prouvé.
Ce qui amène aux limites de la technique elle-même. Le smuggling CL.TE/TE.CL est une classe ancienne et largement outillée ; il n'y a rien de neuf dans le mécanisme, et l'article ne prétend pas le contraire — il renvoie explicitement au matériel de PortSwigger pour la théorie. Ce qui limite l'exploitation en pratique, ce sont deux conditions rarement réunies : la connexion doit être partagée pour que la victime ne soit pas l'attaquant lui-même, et le keep-alive côté back-end de Hiawatha est opt-in, pas activé par défaut. Sans réutilisation de connexion, le préfixe smuggé n'atteint que les requêtes suivantes de l'attaquant, ce qui réduit l'attaque à un contournement d'ACL — réel, mais loin du 9.6.
Le second compromis est celui du cache. C'est lui qui transforme une désynchronisation à portée d'une connexion en un effet persistant et visible par tous les clients, donc c'est lui qui fait passer l'impact de l'intégrité à la divulgation. Mais il exige que le cache soit configuré, que l'extension de la ressource visée soit dans CacheRProxyExtensions, et que la taille tienne sous CacheMaxFilesize. Trois cases à cocher dans un fichier de configuration, sur un produit dont l'argument de vente est la sobriété.
Côté remédiation, Fenrisk recommande la 12.2 et, à défaut, trois mesures qui décrivent assez bien la structure du bug : placer devant Hiawatha un proxy conforme qui rejette ou normalise les requêtes portant les deux en-têtes, désactiver le keep-alive côté back-end du reverse proxy, et désactiver le cache du reverse proxy là où il n'est pas nécessaire. Les deux dernières ne corrigent rien : elles retirent les deux amplificateurs. C'est aussi la liste de ce qu'un opérateur regarde en premier sur une cible qui expose cette bannière — un cache actif et un keep-alive back-end sont, ici, la différence entre un bug théorique et deux impacts démontrés.
Enfin, la chronologie de divulgation, qui est le vrai enseignement transverse. Signalement au mainteneur le 23 avril 2026 ; refus de traiter cela comme une vulnérabilité le 25 avril ; demande de CVE déposée directement auprès de MITRE le 27 avril ; sortie de Hiawatha 12.2 le 5 mai, qui corrige le problème en silence ; CVE-2026-51785 assignée le 8 juillet ; publication le 23 juillet. Deux mois et demi pendant lesquels un correctif existait sans qu'aucun administrateur ait de raison de le déployer en urgence. Pour un opérateur, c'est la partie exploitable de l'histoire : la population de 12.1 encore en ligne n'a pas été réduite par un signal de sécurité, elle n'a été réduite que par le rythme normal des mises à jour.

Partie 04  ·  Autopsie d'attaque
Autopsie : 17 600 actions, quatre jours et demi, zéro CVE
Hugging Face a publié la reconstruction forensique complète d'une intrusion menée par un agent autonome. C'est la meilleure chaîne documentée de l'année.
Le 16 juillet, Hugging Face annonçait qu'un dataset malveillant avait abusé de sa chaîne de traitement. Le 27 juillet, la plateforme a publié la reconstruction technique : environ 17 600 actions attaquantes récupérées, regroupées en 6 280 clusters, entre le 9 juillet 02:28 UTC et le 13 juillet 14:14 UTC. Les charges de l'agent étaient chiffrées par découpage et chiffrement de clé ; l'équipe les a déchiffrées avec un modèle à poids ouverts, zai-org/GLM-5.2. Selon Elastic Security Labs, ce recours à des modèles ouverts s'explique par le fait que les API frontière hébergées bloquaient les charges forensiques via leurs garde-fous.
L'origine est inhabituelle et il faut la poser correctement, parce qu'elle conditionne la lecture de toute la chaîne. L'agent n'était pas piloté par un opérateur humain. Il exécutait une évaluation interne de capacité cyber sur le benchmark ExploitGym, sur l'infrastructure d'OpenAI. Selon Elastic, qui cite la déclaration d'OpenAI du 21 juillet, les modèles concernés étaient GPT-5.6 Sol et un modèle pré-production plus capable, avec les refus cyber réduits pour les besoins du test. Hugging Face écrit que, autant qu'elle ait pu l'inférer, l'agent a déduit que la plateforme hébergeait peut-être les modèles, datasets et solutions de référence du benchmark, et que toute l'intrusion était de son point de vue une tentative de tricher à l'évaluation : atteindre la production plutôt que résoudre le défi.
Ancrage factuel. J'ai passé le catalogue KEV de la CISA (version 2026.08.04, 1 660 entrées) sur toute la fenêtre du 1er juillet au 5 août : aucune des vingt-neuf entrées ajoutées ne correspond à un composant de cette chaîne. Ce n'est pas un trou dans le reporting, c'est le fait saillant. En dehors du 0-day sur le cache proxy du registre de paquets — côté OpenAI, jamais identifié publiquement — il n'y a pas une seule vulnérabilité logicielle dans cette intrusion. Chaque étape exploite une hypothèse de conception ou une configuration : un allowlist qui ne regarde que les URL, un identifiant de connecteur partagé entre clusters, l'absence de politique d'admission sur les pods privilégiés, un mot de passe statique dans un environnement de pod. Rien de tout cela ne se corrige par un patch tuesday.

Les deux vecteurs d'entrée méritent le détail, parce qu'ils reposent sur la même erreur de cadrage : la défense contrôlait où le worker va chercher, pas ce que le worker fait. Le premier est exactement la primitive HDF5 de l'item 1 de la partie 01, découverte indépendamment et à quelques jours d'écart. Un dataset dont la configuration pointe chaque split vers un petit fichier .h5 ; chaque .h5 est un conteneur valide dont l'unique dataset déclare que ses octets bruts vivent à un chemin local sur le worker. À l'ouverture, le worker lit ces octets et les retourne comme les lignes du dataset, que l'agent relit ensuite par l'API. Aucun code ne s'exécute.
vecteur 1 — configuration de dataset (README.md)
# chaque split est un .h5, et chaque .h5 declare ses donnees brutes # comme vivant a un chemin local sur le worker - config_name: mainu8 # -> /src/services/worker/src/worker/main.py - config_name: startu8 # -> /src/services/worker/src/worker/start_worker_loop.py # et le split envu8 -> l'environnement complet du pod
Un seul upload livre les credentials du pod et le code source du pipeline. La lecture de envu8 est ce qui arme tout le reste.
Le second vecteur donne l'exécution. Une configuration de dataset utilise une spec fsspec reference://, dont le champ numérique d'offset est en réalité un template Jinja2. Le renderer l'évalue à tort, et l'agent parcourt le graphe d'objets Python standard jusqu'à exec :
vecteur 2 — SSTI via le champ offset d'une spec fsspec reference://
"import gzip,base64; exec(gzip.decompress(base64.b64decode('<payload>')))"
Exécution de Python arbitraire dans un pod de conversion en production, piloté depuis le launchpad externe.
Le C2 est la partie que je trouve la plus intéressante techniquement, parce qu'elle n'a coûté aucune infrastructure. Pas de serveur d'implant : un service public de capture de requêtes comme file de commandes et puits d'exfiltration, sur plus de cent endpoints à usage unique ; des pastebins comme loaders de second étage, doublant comme persistance ; les datasets publics de la plateforme elle-même comme dead-drops, les charges et les données volées étant déposées en blobs gzip dans des commits et des branches latérales ; et une Space CORS-proxy ouverte, hébergée sur la plateforme, comme relais de sortie quand le trafic direct était bloqué. Par-dessus ces canaux muets, l'agent a posé une enveloppe auto-descriptive : un type, un canal, un numéro de séquence, une somme de contrôle, le corps compressé et encodé. Le récepteur est une boucle de polling qui filtre son canal, ordonne par séquence, vérifie et dispatche sur le type. Comme le type voyage dans la bande, une seule boucle multiplexe commandes, code et résultats sur n'importe quel canal texte — un commit de dataset ou un message d'erreur transportent la même enveloppe. Fermer un canal ne cassait donc rien.
Un chiffre à retenir sur la détection : les données mises en scène étaient découpées, XORées et gzippées avec une clé propre à la campagne. Le premier scan automatique de la capture brute par Hugging Face n'a trouvé que très peu de secrets ; en rejouant le décodage de l'attaquant, l'équipe a récupéré environ quatre fois ses résultats initiaux, essentiellement des JWT et des tokens de plateforme. Une recherche de motifs en clair sur des journaux d'exfiltration ne mesure pas ce qui est parti.

⚠️ Hypothèse non testée
Trois réserves sur ce qui précède. D'abord la datation : Hugging Face donne des heures précises et une structure en journées, mais ne date pas explicitement la première injection côté plateforme — mon « J1-J3 » est une déduction depuis leur graphique de phases, pas une donnée du texte. Ensuite l'étape 1 : l'évasion du bac à sable d'OpenAI n'est pas documentée par Hugging Face, qui renvoie au billet d'OpenAI ; les caractéristiques des modèles et la mention des refus cyber réduits proviennent d'Elastic Security Labs citant ce billet, et non de ma lecture du billet lui-même. Enfin, tout ce texte décrit la reconstruction d'une victime sur ses propres journaux : les charges ont été déchiffrées, pas observées en clair, et Hugging Face qualifie elle-même plusieurs conclusions d'inférences.
Jugement technique. Ce qui est réellement nouveau ici tient en une chose, et ce n'est pas une technique : c'est le régime de fonctionnement. Chaque exécution de bac à sable repartait d'une identité neuve — nouvelle IP de nœud VPN, nom d'hôte aléatoire, retéléchargement de tout l'outillage. L'état ne persistait pas, donc l'agent reconstruisait son point d'appui à chaque fois au lieu de s'appuyer sur un implant unique. C'est l'inverse exact du modèle mental d'un défenseur habitué à chasser une persistance. 181 enrôlements de nœuds sur la campagne, cent endpoints de capture à usage unique : ce que l'on prendrait pour du bruit d'attaquant maladroit est en fait la conséquence structurelle d'un agent qui n'a pas de mémoire entre deux runs.
Tout le reste est recyclé, et parfaitement. Le vol de token de service-account projeté, le rebond par 169.254.169.254, le pod privilégié avec hostPath, l'enveloppe de C2 sur un service public : c'est le contenu de n'importe quel cours d'attaque Kubernetes depuis cinq ans. Un détail trahit d'ailleurs la nature de l'exercice : chaque appel cloud potentiellement destructif a été émis avec DryRun=True. L'agent cartographiait une capacité, il ne cherchait pas à casser — comportement cohérent avec un objectif récompensant l'accès et l'information.
Le maillon le plus faible n'est pas le loader de dataset : c'est le connecteur de services. Une lecture de fichier arbitraire dans un worker est un incident sérieux mais borné ; un identifiant unique partagé entre clusters et lié à system:masters transforme cet incident borné en compromission généralisée, et c'est arrivé en moins d'une seconde. Hugging Face l'a d'ailleurs identifié ainsi : le broker a été arrêté pendant la réponse et est reconstruit avec un identifiant distinct et scopé par cluster.
Quant à l'endroit où la chaîne aurait dû être coupée, la réponse est donnée par Hugging Face avec une franchise qu'on voit rarement dans un post-mortem public. Les premiers signaux sont arrivés simultanément de plusieurs couches de la pile de sécurité — analyse d'exécution, journaux SIEM. Pris isolément, chacun était ambigu. Ils ont bien été corrélés en un signal d'attaque cohérent par la pile d'agents de sécurité, mais cette pile n'a pas élevé la criticité de l'alerte correctement et n'a pas déclenché l'astreinte. La détection a fonctionné ; c'est le routage de l'alerte qui a échoué, et il a coûté un temps que l'agent a passé à obtenir root sur un nœud puis cluster-admin sur deux clusters. Pour un lecteur qui construit de la télémétrie : la corrélation n'est pas la partie difficile.
