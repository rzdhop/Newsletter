› Tomcat : le fix de CVE-2026-29146 a déplacé une accolade et transformé l'EncryptInterceptor en fail-open. Un paquet non chiffré envoyé au port 4000 atteint ObjectInputStream.readObject() sans filtre — RCE non authentifié (CVE-2026-34486), déjà exploité.
› N-central : CVE-2026-18577 n'est pas un nouveau bug, c'est le correctif incomplet de CVE-2026-18556. Contournement d'auth exploité dès le 1er août, puis Take Control vers les endpoints managés et tunnel Cloudflare pour la persistance.
› Titan Quest : Synacktiv dérive un integer overflow 32-bit dans un loader de niveau vers du ROP, en groomant le Segment Heap avec 128 Mo d'eau et 128 WaterLayers à adresses prévisibles.
› À faire aujourd'hui : inventorier les clusters Tomcat avec EncryptInterceptor actif, vérifier ≥ 9.0.117 / 10.1.54 / 11.0.21 et fermer le port 4000 au réseau. Échéance KEV fédérale : 7 août.

Le fil de la semaine
Huit items retenus. La semaine tourne autour de correctifs qui rouvrent la faille, et d'une vague KEV de quatre CVE en trois jours.
Deux des histoires les plus nettes de la semaine ont la même forme : le correctif est la vulnérabilité. Partie 02  ·  Deep-dive
Fail-open par accolade : CVE-2026-34486, le fix qui a rouvert l'EncryptInterceptor de Tomcat
Une accolade déplacée transforme un canal de cluster chiffré en sink de désérialisation Java non authentifié.
Apache Tombat Tribes est la couche de communication de groupe qui fait la réplication de session dans un cluster Tomcat. Les nœuds s'échangent des messages sérialisés Java sur le réseau, et parce que ce trafic est censé rester entre membres de confiance, la réception désérialise sans filtre : XByteBuffer.deserialize() instancie un ObjectInputStream nu et appelle readObject(). La seule chose qui doit garantir cette confiance quand le réseau n'est pas isolé, c'est l'EncryptInterceptor, placé en tête de la chaîne d'intercepteurs : il déchiffre les messages entrants avant qu'ils n'atteignent GroupChannel.messageReceived(). Tant que le déchiffrement échoue sur des octets non authentifiés, la désérialisation ne doit jamais être atteinte. C'est exactement cette garantie que CVE-2026-34486 casse.
Pourquoi la réception désérialise-t-elle sans filtre ? Parce que le modèle de confiance de Tribes est celui d'un réseau de cluster fermé : les membres sont censés être les seuls à parler sur ce canal, et le chiffrement de l'EncryptInterceptor est justement le mécanisme qui remplace l'isolation réseau quand celle-ci n'existe pas. Le readObject() sans ObjectInputFilter n'est donc pas un oubli isolé : c'est une dépendance assumée sur l'intercepteur. Retirez la garantie de déchiffrement, et le sink redevient ce qu'il a toujours été sous le vernis : une désérialisation Java arbitraire ouverte au réseau.
L'ironie est que la faille naît d'un correctif de sécurité. En février 2026, l'EncryptInterceptor utilisait AES/CBC/PKCS5Padding par défaut : CVE-2026-29146, un padding oracle (le CBC permet à un attaquant, en observant les erreurs de padding, de déchiffrer ou forger des messages sans la clé). Le commit 6d955cc (13 mars) corrige ça en modernisant tout le support d'algorithmes : AES/GCM/NoPadding devient recommandé et délégué à un GCMEncryptionManager dédié, et une couche de validation bloque désormais les modes dangereux — NONE, ECB, PCBC, CTS, KW, KWP, ainsi que CBC/CFB/OFB en NoPadding et GCM avec padding. Un vrai durcissement. Mais au milieu de ce refactor, la méthode messageReceived() est réorganisée et l'appel super.messageReceived(msg) se retrouve hors du bloc try. C'est tout. Une accolade, noyée dans un changement par ailleurs légitime — exactement le genre de régression qu'une revue centrée sur « les nouveaux modes sont-ils corrects ? » ne voit pas.
EncryptInterceptor.java — le déplacement d'une accolade
// AVANT (<= 11.0.18) : fail-closed try { data = encryptionManager.decrypt(data); xbb.clear(); xbb.append(data, 0, data.length); super.messageReceived(msg); // atteint UNIQUEMENT si decrypt() a réussi } catch (GeneralSecurityException gse) { log.error(sm.getString("encryptInterceptor.decrypt.failed"), gse); } // APRÈS le refactor 6d955cc (9.0.116 / 10.1.53 / 11.0.20) : fail-open try { data = encryptionManager.decrypt(data); xbb.clear(); xbb.append(data, 0, data.length); } catch (GeneralSecurityException gse) { log.error(sm.getString("encryptInterceptor.decrypt.failed"), gse); } super.messageReceived(msg); // s'exécute MÊME si decrypt() a levé
Diff reconstruit à partir des commits 6d955cc (régression) et 1fab40c (correctif). Dans la version fail-open, une GeneralSecurityException est journalisée puis ignorée : le flux continue avec les octets bruts non déchiffrés dans le XByteBuffer.
Le déroulé de l'attaque suit mécaniquement. On envoie au récepteur des octets qui ne sont pas chiffrés avec la clé du cluster. decrypt() lève GeneralSecurityException, qui est capturée et simplement journalisée. Mais comme super.messageReceived(msg) est désormais hors du try, il s'exécute quand même — en transmettant le XByteBuffer tel quel, c'est-à-dire les octets attaquant bruts, à l'étage supérieur. Ces octets remontent jusqu'à GroupChannel.messageReceived() puis XByteBuffer.deserialize(), où un ObjectInputStream sans ObjectInputFilter appelle readObject(). On a un sink de désérialisation Java non authentifié, joignable en TCP direct.
Paquet Tribes brut vers le NioReceiver (0.0.0.0:4000)
[ "FLT2002" ] // 7 octets : début de message [ int32 length ] // longueur du payload [ ChannelData enveloppe ] // adresse de membre synthétique, options [ objet Java sérialisé ] // CommonsCollections6 (ysoserial) [ "TLF2003" ] // 7 octets : fin de message // Réception : decrypt() lève, l'exception est loggée, puis : GroupChannel.messageReceived() → XByteBuffer.deserialize() → new ObjectInputStream(...).readObject() // aucun filtre → HashSet.readObject() → TiedMapEntry.hashCode() → LazyMap.get("poc") → ChainedTransformer → Runtime.getRuntime().exec(cmd)
Chaîne CC6 (JDK 8–21). L'enveloppe Tribes n'a aucune protection cryptographique propre : seul le contenu était censé être chiffré, et c'est ce chiffrement que le fail-open contourne.
Chaîne d'exploitation (d'après la PoC 404-src et l'analyse Striga)
1
 Atteindre le NioReceiver : par défaut il écoute sur l'interface primaire (pas localhost), port 4000, et accepte une connexion TCP directe. Aucune adhésion multicast requise — tout hôte qui joint le port peut envoyer un message.
2
 Générer un payload ysoserial CommonsCollections6 encapsulé dans l'enveloppe Tribes (en-tête FLT2002, ChannelData, footer TLF2003), sans chiffrement.
3
 Envoyer le paquet : decrypt() échoue, l'exception est capturée et journalisée, mais super.messageReceived() force le passage des octets bruts à l'étage supérieur.
4
 readObject() reconstruit le HashSet : hashCode() déclenche la chaîne LazyMap → ChainedTransformer → Runtime.exec() avec les privilèges du process Tomcat.
5
 Sans gadget sur le classpath, la désérialisation a quand même lieu — prouvable via un gadget URLDNS (callback DNS) — mais l'exécution de commande exige au moins une bibliothèque gadget (Commons Collections, souvent présente via Spring ou Hibernate).
L'exposition réelle dépend de la configuration, et Striga est honnête là-dessus : il faut que le clustering Tribes soit explicitement activé et que l'EncryptInterceptor soit en usage — sinon il n'y a rien à contourner. Mais quand ces conditions tiennent, le modèle de menace s'inverse : l'intercepteur était précisément ce qui permettait de faire tourner un cluster sur un réseau non isolé, et il devient le vecteur. Le NioReceiver se lie à l'interface primaire (pas à localhost) et accepte une connexion TCP directe sur le port 4000 ; aucune adhésion multicast n'est requise. En environnement Kubernetes sans NetworkPolicy, n'importe quel pod du même namespace atteint ce port. Le facteur limitant devient la présence d'un gadget : sur un classpath Tomcat nu, la désérialisation se produit — prouvable via un callback DNS avec le gadget URLDNS — mais l'exécution de commande exige au moins une bibliothèque gadget. Or Commons Collections arrive très souvent de manière transitive via Spring, Hibernate ou des frameworks similaires, ce qui rend la condition « gadget présent » fréquente en production plutôt qu'exotique.

La 11.0.x n'est vulnérable qu'en 11.0.20 : la régression 6d955cc et son correctif 1fab40c encadrent une seule version. Les branches 9.0 et 10.1 ont reçu le refactor plus tôt, d'où une fenêtre vulnérable plus large.
Limites et conséquences. Le correctif 1fab40c est littéralement un « partial revert » : il remet super.messageReceived(msg) à l'intérieur du try, de sorte qu'un échec de déchiffrement redevient un abandon silencieux du message. Côté exploitation, la fiabilité est excellente : pas de corruption mémoire, pas de course, juste une logique inversée ; le seul aléa est le gadget disponible sur le classpath cible. Côté défenseur, le coût d'observation est faible mais réel : la version fail-open journalise encryptInterceptor.decrypt.failed à chaque tentative — un flot d'erreurs de déchiffrement sur le port Tribes est la signature la plus directe. Enfin, cette CVE n'est pas théorique : Unit 42 [4] l'attribue à des tentatives de reverse shell contre neuf serveurs Tomcat dans la phase manuelle de la campagne knaithe, et CISA l'a placée au KEV le 4 août.
Le vrai enseignement est de classe, pas de produit. Un fail-open né d'un refactor de sécurité — déplacer une ligne hors d'un try en croyant « nettoyer » la gestion d'erreur — est une des régressions les plus discrètes qui soient : le code compile, les tests fonctionnels passent (les messages légitimes sont bien chiffrés, donc decrypt() ne lève jamais), et rien ne signale que le chemin d'erreur est devenu un chemin de succès. C'est la même morale que la partie 04, vue depuis le code source plutôt que depuis l'incident.

Partie 03  ·  Deep-dive
De la .map au ROP : exploitation heap de Titan Quest sur Segment Heap
Synacktiv dérive un integer overflow 32-bit dans un loader de niveau vers du ROP, en groomant le Segment Heap avec 128 Mo d'eau.
Le modding de jeu est une surface d'attaque native sérieuse : des fichiers non fiables, parseurs en C++ hérité, et souvent des builds 32 bits où l'ASLR est partiel. Thomas Dubier (Synacktiv) prend Titan Quest Anniversary Edition v2.10.21415 (Windows 11, build 26200, binaire 32 bits) et montre la chaîne complète : d'un integer overflow dans le chargement d'un niveau jusqu'à l'exécution de code, via un groom déterministe du Segment Heap. La distribution GOG embarque les outils de développement, donc un attaquant peut fabriquer des cartes personnalisées chargées depuis Documents\My Games\...\custommaps : le vecteur, ce sont les formats .map (monde), .lvl (niveau) et .pfx (particules).
Le bug primaire est dans GAME::ImpassableData::Load (Engine.dll). La fonction lit width et height depuis le .lvl, alloue un buffer via operator new[](width * height), puis recopie count octets par memcpy. Deux défauts se composent : la multiplication width × height déborde en 32 bits (allocation minuscule), et count, lu indépendamment du fichier, n'est jamais borné contre la taille allouée. Un heap overflow classique, mais dans un tas moderne.
GAME::ImpassableData::Load (Engine.dll) — décompilé
bool *buffer = (bool *)operator new[](this->__width * this->__height); // ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ // mult. 32-bit : déborde → alloc minuscule memcpy(buffer, binaryRead->currentPtr, count); // ^^^^^ lu depuis le .lvl, non borné vs alloc
Chunk .lvl de type 0x03. La même classe de défaut se retrouve dans GAME::EmitterData::InternalBinaryRead (fichiers .pfx), où six compteurs (count1..count6) pilotent des écritures dans une structure de taille fixe sans borne.
Avant le groom, un mot sur les défauts secondaires, car ils comptent pour la fiabilité. GAME::EmitterData::InternalBinaryRead (fichiers .pfx, signature PFX1) offre six chemins d'écriture distincts où un compteur lu du fichier (count1 à count6) pilote une copie dans une structure de taille fixe : tableaux de chaînes, de booléens, de DWORD, données de courbe. Ce sont autant de primitives d'écriture contrôlée utilisables pour faconner le tas ou corrompre un objet voisin, en complément de l'overflow d'ImpassableData.
Le cœur du travail, c'est le groom, et il repose entièrement sur le comportement du Segment Heap de Windows 11. Les allocations supérieures à 0x4000 octets ne passent pas par le LFH mais par le backend Segment Heap, avec des motifs de réutilisation FIFO : en libérant puis réallouant des blocs de même classe de taille, on obtient une disposition prévisible. Dubier détourne GAME::Water::Load pour pulvériser jusqu'à 128 Mo : 128 objets WaterLayer, chacun portant un champ noiseTextureName jusqu'à 1 Mo. Chaque allocation de 1 Mo réserve des pages alignées, si bien que le contenu se répète à des adresses dont les 12 bits de poids faible sont prévisibles (forme XXXXX000). C'est là le contournement d'ASLR : on n'a pas besoin de fuiter une adresse, on remplit assez d'espace pour qu'une adresse fixe tombe de manière fiable dans le spray — et plusieurs DLL 32 bits du jeu n'ont de toute façon pas d'ASLR, ce qui fournit le gadget à adresse constante. Le premier .map prépare la disposition ; le second déclenche l'overflow, plaçant le buffer malveillant juste avant un objet Level.
Le détournement de flux passe par une vtable. On corrompt le membre water de l'objet Level pour qu'il pointe vers un faux Water dont le pointeur de vtable WaterLayer est contrôlé. Au traitement du chunk 0x09 (eau), le destructeur GAME::Water::~Water appelle indirectement (*layer)->vtable->release(*layer, 1) — un appel indirect sur des données entièrement pilotées par le spray.
Détournement de vtable + pivot ROP
// Destructeur GAME::Water::~Water : appel indirect sur structure contrôlée (*layer)->vtable->release(*layer, 1); // layer pointe dans le spray de 128 Mo // Gadget de pivot (Engine.dll, image sans ASLR en 32-bit) 0x10021b91 : xchg esp, eax ; pop edi ; pop esi ; pop ebp ; pop ebx ; ret // ^ EAX = pointeur heap contrôlé ⇒ bascule de pile ⇒ chaîne ROP
Le xchg esp, eax fait de la pile une zone heap contrôlée ; la chaîne ROP rend ensuite le heap exécutable et saute au shellcode. L'encodage de heap du NT Heap n'entrave pas la chaîne car le détournement intervient avant la vérification de désallocation.
La chaîne, de bout en bout
1
 Premier .map : Water::Load alloue/libère pour installer une disposition FIFO prévisible dans le Segment Heap (allocations > 0x4000).
2
 Spray : jusqu'à 128 WaterLayer × 1 Mo de noiseTextureName → 128 Mo à des adresses XXXXX000, contournant l'ASLR partiel du build 32-bit.
3
 Second .map, chunk .lvl 0x03 : l'integer overflow d'ImpassableData::Load produit une alloc minuscule, puis memcpy écrit count octets au-delà, juste avant un objet Level.
4
 Le membre water de Level est réécrit pour pointer vers un faux Water à vtable contrôlée.
5
 Chunk 0x09 : le destructeur Water appelle (*layer)->vtable->release ; le gadget xchg esp, eax pivote la pile.
6
 La chaîne ROP rend le heap exécutable et transfère l'exécution au shellcode déposé dans le spray.
Primitive Fichier / chunk Contrôle attaquant Contrainte
Integer overflow → heap overflow .lvl / 0x03 width, height, count, contenu alloc doit tomber dans Segment Heap (>0x4000)
Écritures OOB secondaires .pfx (PFX1) count1..count6, tableaux structure de taille fixe
Spray déterministe .map / Water::Load 128 × 1 Mo = 128 Mo adresses XXXXX000, ASLR partiel 32-bit

Toutes les valeurs proviennent du write-up Synacktiv. La cible est un binaire 32-bit spécifique (v2.10.21415) — les offsets et l'adresse du gadget sont liés à cette build.
Limites et coût. Le vecteur suppose que la victime charge une carte fournie par l'attaquant : c'est un problème de distribution (partage de mods, dépôts communautaires) plutôt qu'un RCE réseau, et la chaîne est liée à une build 32 bits précise — changer de version déplace les offsets et l'adresse du gadget. La déterminisme repose sur deux propriétés du Segment Heap Windows 11 (seuil 0x4000, réutilisation FIFO) et sur l'absence d'ASLR de certaines DLL du jeu ; un build durci (ASLR complet, /GS, CFG) casserait le pivot. Côté défenseur, il n'y a pas de télémétrie utile sur un jeu grand public : l'intérêt du papier n'est pas la détection mais la méthode — comment un integer overflow banal redevient exploitable en 2026 quand on maîtrise le comportement du tas moderne. Aucune CVE n'est assignée ; le contact éditeur remonte au 15 avril, publication le 29 juillet.
